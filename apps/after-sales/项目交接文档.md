# 迈杰服务项目交接文档

交接日期：2026 年 10 月 20 日

## 一、项目概况

迈杰服务是迈杰平台内的业务应用，用于管理项目从售前、售中到售后的服务流程，同时提供人员协同、资料管理、工单反馈、奖励和结算等功能。

对外名称为「迈杰服务」，代码中的应用标识、目录名和接口前缀仍为 `after-sales`，不是只包含售后业务。

项目分为两个端：

- **管理端**：面向公司内部人员，通过钉钉登录，在平台内使用，已部署使用。
- **微信小程序端**：面向现场服务人员，用于查看被指派的任务、提交现场资料、上传附件及反馈问题等。**小程序代码已放在项目文件夹内，曾进行开发和联调，但尚未正式上线微信，目前暂时搁置。**

管理端和小程序端面向不同人员，使用各自的操作界面，通过后端服务共享业务数据。

## 二、主要业务功能

| 功能模块 | 主要作用 |
| --- | --- |
| 总览 | 展示授权范围内的项目情况、本人待办、临近到期及逾期风险等。 |
| 售前服务 | 对接 CRM 项目，管理售前节点、项目人员、多轮推进、附件、项目信息和版本留痕；提供统计分析。 |
| 售中服务 | 承接售前结束后的项目，选择实施节点、指派现场人员、维护进度及交付资料，并查看售前资料和商城方案。 |
| 售后服务 | 管理现场服务、寄件售后、驻校巡检等任务及完工资料。 |
| 工单与反馈 | 记录、分派和处理业务问题及现场反馈。 |
| 服务团队 | 管理小程序注册人员的资料、审核状态、服务能力和标签。 |
| 服务奖励 | 维护人员奖励；实物奖品从设置中的奖品目录选择。 |
| 结算中心 | 登记售中、售后的费用结算、收款及开票情况，保留财务操作留痕。 |
| 设置 | 管理应用权限、标签库、实物奖品等配置。 |

### 业务来源与系统联动

- 售前列表同时包含 CRM 同步项目和在本应用手动新增的独立项目。CRM 项目到「方案渗透」及后续阶段才进入售前，且只展示当前用户在 CRM 中有权查看的项目。
- CRM 来源的项目名称、客户、销售负责人等基础信息由 CRM 维护；售前流程、人员、轮次、附件及项目补充信息由迈杰服务维护。本地新增项目不自动关联或写回 CRM。
- 售前的设计负责人、方案负责人各为单选；节点项目人员支持多人，每个人可分别填写工作说明。售前人员从钉钉通讯录选择。
- 售前详情的「项目信息」集中维护面积、项目等级、紧急程度、预计招标时间、项目需求文档等内容。费用为项目级只读数据：预计费用来自 CRM，对外报价和实际费用通过正式接口读取商城的业务员报价总价和 A1 总价。
- 售前完成「售前项目结束」时，按选定节点自动创建关联售中项目；重复提交不会重复建项。售中通过「售前资料」查看原售前资料，并通过既有入口打开商城方案。
- 售中、售后的现场执行人来自已审核的微信服务团队。人员注册后先进入待审核名单，审核通过后才可被指派任务。
- 售前不参与服务结算；售中、售后节点通过不以费用先结清为前提。结算中心用于业务登记，不直接执行银行转账或税务开票。

### 权限划分

| 角色 | 权限范围 |
| --- | --- |
| 业务员 | 总览、售前、售中、售后、工单与反馈、结算中心；服务团队仅查看。 |
| 服务管理员 | 包含业务员权限，增加服务团队审核及操作、服务奖励管理等权限。 |
| 系统管理员／应用管理员 | 本应用全部权限，包括设置和权限配置。 |

没有上述有效权限的内部人员不能使用管理端；无权限页面不显示入口，后端也独立校验。应用权限不会扩大 CRM 项目的可见范围，也不会解除历史节点、旧轮次或已审核资料的只读限制。

## 三、代码位置与项目结构

服务器上的实际应用目录为：

```text
/usr/local/mj_program_platform/apps/after-sales/
```

接手或使用导出的平台源码时，以其中的 `apps/after-sales/` 为当前应用代码，不要把 `program_resource/after-sales/` 中的原型或参考资料当作线上运行代码。

| 路径（相对应用目录） | 内容 |
| --- | --- |
| `frontend/` | 管理端代码，使用 Vue 3、Vite 等构建。 |
| `backend/` | Django 后端，提供项目流程、人员、附件、权限等业务接口。 |
| `miniapp/` | 微信小程序完整源码及构建配置，使用 uni-app、Vue 3、TypeScript。 |
| `miniapp/src/` | 小程序页面、组件、接口调用等源代码。 |
| `miniapp/dist/build/mp-weixin/` | 小程序构建产物，生成后由微信开发者工具导入；不作为源代码维护。 |
| `manual-renderer/` | 产品说明书等资料预览相关的渲染辅助服务。 |
| `app.manifest.yaml` | 本应用服务、路由、数据库、持久卷等部署声明。 |
| `README.md` | 业务规则、接口说明和开发验证命令。 |
| `DEPLOYMENT.md` | 部署、备份、恢复及小程序发布操作说明。 |

后端生产环境使用独立 PostgreSQL，私有附件存储在持久卷中。仅复制源码不等于复制完整运行环境，数据库、上传附件和密钥配置需分别交接；密钥不应写入文档或源码包。

## 四、小程序端交接状态：代码保留，暂未上线

**小程序端代码已经包含在本项目的 `miniapp/` 文件夹中，不是缺失或需要重新开发；但还没有发布为普通微信用户可使用的正式小程序，目前暂时搁置。**

已有开发内容包括微信登录与人员注册、审核状态展示、售中／售后任务、现场资料及附件提交、产品资料查看、反馈／工单和个人记录等。小程序不承接内部售前管理工作。

后续恢复此项工作时，需要：

1. 核对公司小程序账号、开发者权限和 AppID，确认服务器认证配置与小程序一致。
2. 重新构建并联调当前代码，验证注册审核、任务指派、图片／PDF 预览、附件上传、确认完工及两端数据同步。
3. 核对公网 HTTPS、微信合法域名、备案、服务类目及隐私配置，并在不同网络下进行真机验收。
4. 上传体验版，完成微信审核后发布正式版。

公司内部对服务人员的「审核通过」和微信平台的「小程序审核发布」是两回事；前者不代表小程序已经正式上线。历史调试二维码、开发版或体验版也不等于正式发布。

具体构建与联调方法见 [小程序说明](miniapp/README.md)，发布步骤见 [部署手册](DEPLOYMENT.md)。恢复时应重新核对配置与实际状态，不把手册中列出的步骤视为已经完成。

## 五、售前多轮推进与售中资料交接

### 1. 当前已经实现的逻辑

- 新增一轮推进时，**新一轮成果附件为空，不继承上一轮附件**；本轮上传自己的成果文件。
- 新增一轮需要填写原因，也支持添加原因附件。已有新轮次后，旧轮次只读，历史资料仍可查看。
- 售前流入售中后，「售前资料」汇总各节点、各轮的有效成果附件，**不是只取最后一轮的附件**。
- 同一项目内的成果附件按**完整原文件名（含扩展名）**去重，同名只展示最新上传的文件；上传时间相同时，以较大的附件 ID 为准。
- 不同名文件均保留。例如第二轮只更新了 `方案.pdf`，第一轮的 `清单.xlsx` 仍会出现在售中；第一、二轮同名的 `方案.pdf` 则只展示最新版本。
- 售中复用原售前私有附件的访问与预览能力，不物理复制或删除历史文件。同名旧版本仍保留在售前历史轮次中。

这里的「汇总所有文件、同名只取最新」指多轮推进的成果附件。新增一轮的原因附件不混入成果；项目需求文档、普通节点附件及关联记录资料继续按各自规则展示。

**当前限制：按文件名识别是否为同一文件。** 例如 `方案-v1.pdf` 和 `方案-v2.pdf` 会被视为两个不同文件，系统暂时不能判断它们属于同一个固定成果项。

### 2. 后续要调整的目标逻辑——暂未实施

后续售前多轮推进要改为维护一个**固定文件列表**：

1. 先确定售前需要维护哪些文件项，用户上传和更新的成果文件都必须归入列表范围。
2. 多轮推进围绕同一份文件列表维护版本，不再完全依赖用户自由命名来判断文件关系。
3. 售前流入售中时，按列表中的每个文件项提取其最新版本，组成售中可查看的成果资料。

**该改造目前暂时搁置：泮丽姐尚未提供固定文件列表，待清单提供并确认后再实施。当前线上仍执行上一节的「各轮成果汇总、同名只保留最新」逻辑。**

收到清单后，还需结合实际内容确认文件项与节点的对应关系、是否必传，以及历史自由上传文件如何归入列表；这些细节尚未定稿。

## 六、维护与交接注意事项

- 管理端、业务 API、小程序是不同的构建／发布对象；部署服务器不会自动发布微信小程序。
- 常规应用部署入口为平台根目录下的 `bash scripts/app-deploy.sh after-sales server.env.docker`。具体备份、迁移及检查按部署手册执行，不自行另起一套网关或数据库。
- 仅修改本应用时不要顺带重部署 Auth 等公共模块；涉及公共接口或身份配置变化时，应另行评估影响。
- 数据库和附件需配套备份。源码包不包含业务数据，回滚代码也不会自动回滚数据库迁移。
- 接口和资料读取保留逐用户授权。CRM、商城、Auth、产品档案等通过既有 API 集成，不直接访问其他应用数据库。
- 普通业务资料多采用自动保存，结算等操作仍有显式保存；保留已有版本冲突及未保存保护，不用强制覆盖消除冲突。
- 后续联调优先使用隔离测试数据，避免在真实项目中留下无意义的人员变更、版本记录或推进记录。
