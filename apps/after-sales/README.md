# 迈杰服务

App ID: `after-sales`

项目概况、代码位置、小程序未上线状态及售前固定文件列表待办见 [项目交接文档](./项目交接文档.md)。

本应用按平台 App 脚手架建设，覆盖售前、售中、售后服务项目，以及服务人员、奖励、结算和资料的完整协同流程。管理人员只使用钉钉登录的 Web 管理端，服务人员只使用微信小程序，两端不共用操作界面。

## 业务范围

- 管理端桌面售前服务新增「项目列表 / 统计分析」页签。统计默认显示全部项目，可按项目性质、CRM 阶段、销售负责人和设计负责人分组，支持搜索、状态筛选及明细分页；分类、筛选和页码保留在 URL。统计页面按内容自然向下滚动，不强制分组和明细同屏；两块表格独立限制最大高度，数据较多时可在表内滚动，分页跟随明细展示；明细、分组及任务弹窗复用项目列表的表格主题。项目列表上下文保留，点击统计中的项目复用原详情抽屉，关闭后更新统计。手机端和微信小程序维持原有入口。
- 四类分组统计默认展开，可通过标题栏「收起 / 展开」切换，当前页面内各分类分别保留展开状态；折叠后保留当前分组名称和「全部分组」操作，不改变明细筛选、页码或表格滚动位置，也不额外请求接口。
- 统计明细的「项目最新阶段」展示当前售前节点，多个并行节点一并显示；右侧独立展示「CRM阶段」。所有统计视图沿用这一列顺序，按项目阶段分组仍以 CRM 阶段汇总。
- 只读接口 `GET /api/after-sales/presales/statistics` 沿用三类管理角色、有效用户的 CRM 可见范围和「方案渗透」阶段门槛。先汇总完整授权项目，再分页查询描述、人员、任务和原始需求附件；不读其他应用数据库、不写钉钉文档。性质、项目金额、工程面积分别来自 CRM `integrationWorkTypes/amount/integrationEngineeringArea`，设计及方案负责人取自售前立项；本地项目读取已有 `projectInfo`。预计招标时间统一读取本地 `projectInfo.expectedBidAt`，由项目信息页维护，不使用 CRM 投标时间 `bidTime`，未填写显示「未填写」。金额未填与零元分别展示，多性质或历史多人分组的全局项目数去重；完成任务按所属节点已完成状态计算，完成时间取系统记录，不使用已废弃的轮次 `designDate`。统计按需加载，隐藏后停止轮询，CRM 同步期间渐进刷新，身份变化或范围过期清空旧结果；缺少的项目面积、等级等信息不虚构、不拿节点费用代替。
- 售前：19 个业务节点，包含并行任务、持久化审批行与意见历史、中标/未中标分支；费用按整个项目从 CRM 和商城读取，不按节点维护，不参与服务结算。
- 售前节点满足流程前置条件后自动进入进行中，并记录实际开始时间；创建项目时首节点即开始，前期/后期并行分支分别解锁，汇合节点等待所有前置分支通过。管理端不提供售前「开始节点」按钮，已有或手动填写的实际开始时间不覆盖；售中/售后仍由管理端确认开始。`0023_presales_auto_start` 为在途售前的已解锁活动节点补齐缺失开始时间，优先取前置节点通过时间，首节点取创建时间；不改终止、已完成、已删除项目及其他服务类型。
- 售前「节点回退」沿流程依赖定位前置节点，回到已完成节点时重新打开该节点；仅重置该节点及后续依赖节点的完成状态与处理结果，保留另一并行分支和原有开始时间，不以节点序号或列表当前节点限制已到达分支的操作。
- 售前列表、详情顶部、流程摘要及总览展示全部进行中的并行节点，使用轻量 `activeNodes` 摘要，不再只显示 `currentNodeKey`。当前节点筛选在分页前匹配任一启用且进行中的节点；已完成、取消、挂起项目保留其结束/停止节点。列表复用当前页节点预取，总览只批量预取最多 8 个最近项目的活动节点，不读取全量项目节点或轮次资料。
- 售前不对节点排期：立项仍需分派钉钉人员，但不要求节点计划开始/结束时间；旧节点排期只保留历史，不用于校验或超时判断。具体工作每轮只填写「计划开始时间、预计完成时间」，两项均可选，填写计划起止时预计完成不得早于计划开始。没有手填实际完成时间，轮次完成状态跟随所属节点通过，完成后使用系统记录的节点通过时间判断按时/延期完成。原轮次 `designDate` 及派生索引的 `actual_end_date` 仅保留历史，不再用于校验或当前待办/超时判断，附件及备注不变。按上海日期判断延期，预计完成当天不超时；只有最新轮次可修改，新增一轮后此前的时间、附件、备注和新增原因只读。正常删除最后一轮后，当前最后一轮恢复编辑；不能删除历史轮次或通过覆盖数组改写历史。
- `0024_presales_task_schedules` 从售前交付节点的 `schemeRounds` 回填派生排期索引，原 JSON、节点历史时间不改。保存、提交和推进时在同一事务同步该索引；任务预计完成时间及总览按已解锁活动节点中尚未完成的具体任务统计，不对未解锁、已完成、取消、删除项目告警。售前列表以「CRM 阶段」替代预计完成列，显示已同步的 CRM 阶段，本地新增或未填写阶段显示「—」。总览仍在数据库计数，摘要各最多 8 条，避免读取全量项目轮次 JSON。
- 售前节点选定的钉钉执行人，其已解锁活动节点下各轮任务进入个人总览「我的待办」，未填时间的任务同样保留。填写预计完成时间后，按上海日期提前 3 天进入「风险提醒」，当天提示「今天到期」，次日起提示超时天数；临近到期与超时分别统计、不重复提醒。人员更换/移除、节点通过/停用、项目完成/取消/删除后，执行人范围及待办提醒在下次总览刷新时更新。按当前有效 `userId` 匹配，不按姓名或代理操作者匹配。「我的待办」只计入明确分派给本人的未完成任务，未设置执行人或分派给他人的节点不计入。管理端仍须先获得业务员、服务管理员或系统管理员权限，审计创建者和任务分派本身不授予模块使用权；三类角色查看授权范围内的整体风险，微信服务人员仅能看到自己已分派工作的风险。售前仍只按每轮任务的预计完成时间判断，售中/售后按节点计划结束时间判断。CRM 项目继续要求当前账号拥有 CRM 可见权限。
- 售前项目来源：CRM 同步和本地新增并存，进入售前列表时同步当前用户可见且已到「方案渗透」及之后销售阶段的商机，直接创建进行中的售前流程；包含方案渗透、标前准备、挂网投标、中标待签、待审合同、已签合同。在跟线索、确认商机、采购情报池、空阶段及未知阶段不进入售前。本地新增项目独立维护，不关联 CRM，不受该阶段门槛影响。不需要激活，也不要求申请理由。CRM 项目的负责人/申请人统一使用 CRM 负责人，售前不再显示联系电话。
- 售中：8 个项目节点，支持按项目启停施工类节点、六节点人员矩阵、手动计划开始/结束时间和节点交付。
- 售前正常完成「售前项目结束」时，在结束节点中选择售中包含的节点（默认全选，保留项目立项和售中项目结束）；节点选择自动保存，结束售前与创建售中在同一事务执行。新售中继承项目名称、客户、负责人、地址和项目说明，现场执行人仍由已审核的服务团队分派，不复制售前钉钉人员、排期、费用或执行进度。`0025_presales_midsales_handover` 增加唯一的 `presales_project` 关联；重复提交不重复建项，售前回退后再次结束复用原售中而不覆盖其资料。迁移不批量转换历史已结束项目。
- 售中详情新增「售前资料」页，调用管理端 `GET /api/after-sales/projects/{id}/presales-materials`，按原售前节点及关联工单、反馈、资料分组。推进附件汇总各节点全部轮次的成果附件，同一项目内按完整原文件名（含扩展名）去重，仅展示最新上传的版本；上传时间相同时取较大的附件 ID。最新轮为空时仍展示历史轮次的成果，旧轮次继承同一附件 ID 时只计一次；原因附件和未关联任何轮次的提交附件不混入成果。普通节点资料、费用和关联记录附件继续展示，无轮次记录的旧节点保留其原有附件。接口的分组 `itemIds`、分类与数量使用同一筛选结果。只读复用原私有附件预览与下载，不复制或删除原文件，同名旧版本仍可在售前历史轮次查看，展开分组后才加载文件列表。商城方案复用售前提交窗口的统一入口，经 CRM 的授权接口解析，再沿现有钉钉导航打开；独立本地售前未关联商城时明确说明。资料接口同时校验售中与原售前的访问权限，CRM 来源继续检查有效用户权限，微信现场身份不能通过售中关联获得售前附件权限。
- 售后：现场服务、寄件售后、驻校巡检三种互斥服务类型，包含派单信息、产品明细、完工信息和必传凭证校验。
- 微信小程序端：微信首次注册后进入服务团队待审核名单；认证通过后读取已分派的售中、售后任务，与管理端共用 Auth、业务 API 和数据库。
- 管理工作台：服务人员认证、按业务节点维护能力标签、奖励发放、按收费节点结算和资料授权。
- 设置 / 实物奖励：管理员维护可选奖品（添加、改名、停用/启用）；手动新增实物奖励须传入有效 `prizeId`，奖励保存奖品名称快照，历史记录不随目录改名或停用而改变。
- 人员来源：售前项目人员只从 Auth 的钉钉通讯录选择；售中、售后只可指派已审核的微信小程序注册人员。
- 售前设计负责人、方案负责人各限单选，可更换或清空，服务端同样校验每个角色最多一人；两个角色独立保存。各节点项目人员支持多选，弹窗连续勾选，确认后保存；取消不修改已保存人员，支持搜索和移除。节点人员每人独占一行，工作说明按人员 ID 保存在 `members[].note`，可分别填写、清空，自动保存；增减人员保留仍在名单中的个人说明，新人员从空说明开始。历史单人/多人共用的 `note` 在缺少个人说明时按原有人员回显，首次保存后转为个人说明，不回填覆盖显式清空的内容。兼容历史单人配置，服务端按成员派生精确的 `userIds`，全部执行人的个人待办、关联项目和消息范围同时生效；人员配置本身不授予模块权限，也不扩大 CRM 可见范围，历史只读节点仍不可更改人员或说明。
- 管理端的项目人员选择与显示共用一个入口：未选择时显示选择提示，选定后显示人名，点击人名即可更换；售前人员矩阵不另设操作列，交付节点、售中和售后复用同一人员按钮。工单详情在「处理人」字段直接分派/更换；奖励和结算沿用原位显示选值的搜索选框。
- 平台集成：统一登录与会话、代理身份、应用管理员范围、顶部栏、侧边导航和 App manifest 部署。
- 公开示范：`/after-sales/demo/` 只读取一条启用的独立公开资料，不暴露正式项目、任务、人员或私有附件。

## 业务权限

管理端只允许拥有下列至少一项权限的人员使用，同一人员可以兼任；没有默认业务角色。Auth 最终系统管理员能力映射为本应用系统管理员。角色逐级包含基础能力，业务 App 的「系统管理员」不反向授予 Auth 平台管理员能力。

| 权限 | 能力 |
| --- | --- |
| 业务员 `sales` | 使用总览、售前/售中/售后服务、工单与反馈、结算中心；服务团队列表、详情及资质附件仅可查看。 |
| 服务管理员 `service` | 包含业务员全部能力，另外可审核/暂停/恢复服务人员、维护节点能力标签、管理服务奖励。 |
| 系统管理员 `admin` | 本应用全部权限，额外可访问设置、维护安装人员标签库/实物奖品和分配权限。 |

- 未配置任何有效角色的钉钉用户无法进入管理端，业务 API 的读取、写入及附件下载统一返回 `403 APP_ACCESS_DENIED`；会话接口只返回 `canManageApp=false`，用于展示明确的无权限页面，不把业务无权限误当成登录失效。项目负责人、节点执行人、工单处理/提交人、同步触发人和转发链接本身都不授予模块使用权，角色撤销后下一次业务请求即拒绝。新建本地项目时，真实创建者仍自动成为负责人；审计字段 `created_by` 不是访问授权。
- 三类角色的总览展示当前授权范围内的项目统计与风险。「我的待办」始终只计入明确指派给本人的未完成任务，管理员也不会把全部项目任务算为自己的待办。业务员总览不展示奖励数据，服务团队页不请求奖励或显示审核、暂停、能力编辑操作。
- 设置沿用部门、部门及下级、指定人员、排除人员的规则。排除优先于当前权限的直接及部门授权，不影响其他权限；高角色包含低角色能力，无需重复授权。代理身份按当前有效用户计算，不继承操作者权限。无权限的页面不显示菜单入口，直接链接及服务端 API 同样受限。
- 管理端与微信小程序以认证渠道隔离。微信审核、本人任务和附件维护规则继续生效，应用权限配置或 `source=mobile` 参数不能将钉钉身份切换成现场身份。系统管理员仍遵守已结束节点、历史轮次只读和现场资料由现场人员维护的业务规则。
- CRM 来源项目继续与 CRM 当前用户可见范围取交集；商城方案继续经原授权接口访问。转发链接只定位页面，不授予收件人权限。API 在服务端逐项校验角色、项目、节点及附件目标，前端据返回的 `permissions` 同步操作入口。
- `0029_management_roles` 将原 `business` 迁为 `service`、`finance` 迁为 `sales`，`admin` 保留；保留原人员、部门、含下级和排除规则，并递增权限配置版本，阻止旧权限草稿覆盖新角色。部署时执行正常 Django 迁移；本地 SQLite 测试不代替生产 PostgreSQL 迁移验证。
- 专项验证：`manage.py test after_sales_api.test_business_access`；`node --test apps/after-sales/frontend/tests/businessPermissions.browser.test.mjs apps/after-sales/frontend/tests/sessionRenewal.browser.test.mjs`，覆盖三角色准入、无角色用户及分派人员拒绝、角色叠加、排除、代理、撤权、对象与字段范围、双版本保存冲突、管理员全能力、无权限深链接及会话续期。

## 目录结构

- `frontend/src/App.vue`：钉钉管理端的平台外壳、管理路由和会话状态；不提供 Web 现场端入口。
- `frontend/src/components/ProjectWorkspace.vue`：售前、售中、售后项目与节点流程。
- `frontend/src/components/SettlementWorkspace.vue`：结算分页、承担主体、收款/开票流水及更正。
- `frontend/src/components/ResourceWorkspace.vue`：历史业务资源组件，结算实际路由使用 `SettlementWorkspace.vue`。
- `miniapp/`：uni-app + Vue 3 + TypeScript 微信小程序现场端，编译输出到 `miniapp/dist/build/mp-weixin/`。
- `frontend/src/components/AttachmentPanel.vue`：私有附件上传、下载和删除。
- `frontend/src/serviceApi.js`：前端业务 API 契约和字段转换。
- `backend/after_sales_api/models.py`：业务模型、审计字段和数据约束。
- `backend/after_sales_api/views.py`：项目状态机与业务资源 API。
- `backend/after_sales_api/settlement_finance.py`：结算来源分页、权威目录、人员关联项目与财务留痕。
- `backend/after_sales_api/workflow_rules.py`：三类项目节点和转移规则。
- `backend/after_sales_api/attachment_views.py`：附件名称、大小校验及逐目标权限。
- `backend/after_sales_api/provider_self_views.py`：服务人员档案申请和重新提交。
- `backend/after_sales_api/approval_*.py`：售前审批行、不可覆盖版本历史及管理员 API。
- `backend/after_sales_api/capability_views.py`：节点能力标签目录和管理员维护 API。
- `GET /api/after-sales/mobile/v1/home`、`POST /api/after-sales/mobile/v1/tasks/<assignmentId>`：微信现场端版本化任务契约。
- `app.manifest.yaml`：前后端、PostgreSQL、私有上传卷、路由、网络和 Secret 声明。

## 本地校验

### 附件、草稿与历史记录保护

- 微信业务附件每次请求校验服务人员认证状态。暂停或未审核人员不能访问项目、工单等业务附件；本人注册申请的资质附件仍可补充。现场确认完工后，该指派对应的节点附件只读；管理端仍按节点权限维护。审核通过的售中证明材料禁止追加、删除，管理端驳回后才允许更正。
- 普通节点草稿、指派和节点推进携带 `expectedUpdatedAt`，过期返回 `409 PROJECT_NODE_CONFLICT`；售前轮次沿用 `PRESALES_ROUND_CONFLICT`。项目资料使用独立 `draftVersion` / `expectedDraftVersion`，避免节点活动引起误冲突。冲突和网络失败保留当前草稿，允许重试或确认放弃后重新读取；关闭、切节点、导航离开受未保存保护，后台同步不覆盖正在编辑的资料。旧售前审批接口不能写入已结束、取消或禁用的流程，读取已结束节点也不会补建审批行。
- 服务团队、服务奖励、工单与反馈列表沿用现有多列筛选，按服务端每页上限读取完整授权记录，再使用统一分页栏展示（20 / 50 / 100 条）；候选目录也读取完整分页，任何一页失败均明确报错。CRM 项目和结算继续沿用服务端筛选分页，不改为全量加载。
- 微信历史记录使用 `GET /api/after-sales/mobile/v1/records/{feedback|tickets|rewards}?page=1&page_size=20`，仅限本人反馈、本人提交的工单和本人奖励，可用 `recordId` 定位旧记录。小程序反馈/工单每页 20 条、个人页奖励每页 5 条，支持加载更多；`home.recordCounts` 返回完整数量，首页摘要仍限 20 条。工单处理权限保持原规则。
- 管理端采纳反馈可选设置中的有效实物奖品，提交 `reward.prizeId`，服务端以目录名称生成奖励快照。未选奖品只采纳，不再自动生成默认礼品；停用或不存在的奖品拒绝发奖。
- 专项验证：`manage.py test after_sales_api.test_review_regressions`、`node --test apps/after-sales/frontend/tests/autosaveAndPagination.test.mjs apps/after-sales/frontend/tests/reviewRegressions.browser.test.mjs`。浏览器回归使用隔离模拟接口，不写真实业务记录。

### 结算中心

- 服务推进与财务处理独立：售中/售后收费节点无需先结清才能通过，仍需有效现场人员提交完工资料。售前不生成可结算来源，不提供结算跳转，不能作为结算关联项目；服务端创建结算时同样校验，不能绕过页面选择。历史售前费用及财务记录保留原始数据，不计入当前服务结算列表，不删除余额或流水。
- 新来源可直接「保存待结算」，保留部分收款；客户承担的「确认结清」仍需收齐订单金额，结清后可继续逐次登记开票。公司承担按实际成本归集，对外报价独立保存，不拿成本冒充报价。
- 列表 `GET settlement-sources` 使用服务端分页（默认 20、上限 100），支持 `state/type/nodeName/bearer/search/projectSearch/customerSearch/ownerSearch/projectId/sourceNodeId`。表头项目、客户、负责人各有独立搜索框，仅匹配对应列，多个条件在数据库分页前取交集；历史无来源节点记录的客户按该行显示的历史客户快照匹配。响应内含本页有效结算及完整授权范围的节点名称。历史已生成记录不因来源节点后来变动而丢失，无来源节点的旧记录也可查阅。
- 管理端桌面结算列表与项目列表共用 `ListPagination`：左侧总条数、中间数字页码与前后页、右侧每页 20／50／100 条。结算切换每页条数或筛选时回到第一页并保留其他筛选，加载期间禁用翻页与条数切换。
- `GET settlement-companies` 通过本 App 凭据读取 Auth 公司主体；人员复用 `employees/directory` 的 ID/部门/拼音字段。`GET settlement-projects?userId=...` 按负责人、节点执行人、未撤销现场指派的真实 ID 关系筛选售中/售后服务项目，可搜索、分页，保留 CRM 权限。新主体引用保存 `subjectId`，历史名称快照不会按同名自动关联。
- 财务内容改为显式保存，并为关闭抽屉、导航和浏览器离开提供未保存保护。每次 `PATCH settlements/<id>` 必须传 `expectedRevision`；版本过期返回 `409 SETTLEMENT_REVISION_CONFLICT`，页面保留填写、展示最新值，核对后合并本次修改。
- 已保存记录的金额、票据、承担主体和结算说明可直接编辑，点击「保存修改」生效，无需进入更正模式。累计金额与本次收款/开票双向同步；减少金额、调整已结清信息或修改既有票据时自动显示原因，已结清收款不足时保存为待结算。冲突核对保留改动字段；本次登记按累计目标去重且不降低他人新增余额，直接修改累计值按核对后的目标保存。已撤销记录仍只读。
- `SettlementEvent` 逐次记录收款/开票增减、票号、前后快照、有效用户及实际操作者。减少金额、修改既有票据、更正结清信息、恢复待结算及撤销需要 `correctionReason`。更正后未收齐必须恢复待结算；撤销前须冲回余额，撤销记录只读且永久保留留痕，不会删除旧流水。
- 结算详情顶部以「结算详情 / 版本与留痕」分开展示登记与审计，切换保留未保存内容及各页滚动位置；留痕按版本倒序展示操作、上海时间、经办人及金额增减，展开核对变更前后与票据。历史汇总只显示期初值，不标为新增收款；已撤销结算在同一留痕页切换查看。
- 迁移 `0026/0027` 增加版本、主体 ID、独立对外报价及流水表；旧记录以「历史汇总」保留已有余额与原更新时间，不虚构历史逐笔交易。此模块仅记录业务结算，不执行银行收款、转账或税务开票。
- 专项验证：`manage.py test after_sales_api.test_settlement_finance after_sales_api.test_messages_settlements.SettlementSourceApiTests`；`node --test apps/after-sales/frontend/tests/settlementFinance.browser.test.mjs`。真实并发用独立 PostgreSQL 测试数据库验证，SQLite 不具备相同的行锁语义。

## 数据与部署

- 管理端的 Auth 身份和迈杰服务应用权限分别维护，业务权限只以 `/api/after-sales/session/` 的当前账号结果为准，不写入跨应用广播的登录存储。沿用平台每 10 分钟及重新聚焦后的会话校验与钉钉 Cookie 丢失免登恢复；后台重查应用权限，同一身份续期保留当前页面、展开状态和未提交内容。权限接口网络/服务失败时保留界面并显示「重新验证权限」，不误报无权限；权限确实撤销后收起业务入口。跨页面身份/代理变化完整重新加载，迟到的旧权限响应不应用到新身份；后端每次业务请求仍独立鉴权。
- 本地 Django 检查使用 SQLite；生产服务使用 manifest 中独立的 PostgreSQL。
- 私有附件保存在 `after_sales_uploads` 持久卷，不通过前端静态目录公开。
- 管理端与小程序附件均不限文件类型，包括推进资料、交付证明、反馈/工单和资质附件；不要求后缀与 MIME 匹配，无后缀或未知类型同样可上传，单个文件上限仍为 200MB。图片和 PDF 沿用原有预览，其他格式按附件下载；下载接口保留逐目标鉴权，强制附件响应并禁止 MIME 嗅探。空文件、无效文件名、历史只读与已审核材料保护保持生效。
- 模型变更必须同步提交 Django 迁移，不得使用 `--run-syncdb` 代替。
- 应用的常规改动仅限 `apps/after-sales/`，不修改根网关、根 Compose、Auth 或 Portal。

### CRM 售前项目同步

- 后端与商城使用同一正式接口 `GET /api/crm/opportunities`，复用 CRM 按用户权限与数据版本维护的完整响应缓存；不再逐页重复读取 `list-lite`。详情通过 `GET /api/crm/opportunities/<string-id>` 读取，均转发当前用户的 Auth Cookie/Bearer，不使用其他账号或跨应用数据库。只存售前需要的基础字段；完整响应校验通过后先发布当前用户可见范围，让已导入项目立即参与列表与总览，再后台导入/更新服务流程。未知用户且没有有效范围时，仍只显示独立本地项目，不使用全局 CRM 数据代替授权。意外分页、总数不匹配、重复/无效 ID 和格式错误不导入、不续期旧范围。连接重置、超时及 429/502/503/504 最多重试当前 GET 3 次，间隔 250/750 毫秒；401/403、404、无效 JSON 直接失败。服务端默认为 `http://crm-backend:8000/api/crm/`，可用 `CRM_PROJECT_SOURCE_URL`、`CRM_PROJECT_SOURCE_TIMEOUT_SECONDS`、`CRM_PROJECT_SOURCE_SYNC_INTERVAL_SECONDS` 配置（已在 manifest 声明）。
- 使用 `ServiceProject.source_crm_id` 保存字符串商机编号；`(service_type, source_crm_id)` 唯一，CRM 编号相同的售前项目不会重复创建，售中/售后不受此唯一关系限制。迁移为 `0022_crm_presales_source`。
- 同步项目销售和产品销售。项目名称、客户、负责人及项目说明/采购需求由 CRM 维护，管理端只读；CRM 阶段/状态单独展示，不控制售前节点完成状态。申请理由、补充附件、节点人员、计划/实际时间、轮次、费用、结算及操作历史留在服务中心。
- 进入售前页面时按需启动后台同步，HTTP 请求不等待全量项目导入；已有当前用户有效范围时直接读取本地分页，没有有效范围时显示同步提示。同步轮询依次间隔 900/1800/3200 毫秒，随后每 5 秒；普通列表每 30 秒刷新，重新聚焦后按需更新，失败后自动重试，不提供手动刷新按钮。默认每页 20 条，可选 50/100 条；搜索、客户、负责人、当前节点、完成状态和 CRM 阶段在服务端分页前筛选，页码和筛选保留在 URL。CRM 阶段选项从当前账号可见的全部售前项目去重取得，不受当前页或其他筛选条件限制；「无 CRM 阶段」包含本地项目与阶段未填写的 CRM 项目，`crmStage=__empty__`，正常阶段按名称精确匹配。翻页不再把其他所有页读完。前端最多保存 12 个分页/筛选结果，同一有效用户、代理操作者和管理能力下重新进入或重新登录时先显示仍有效的已读列表，再后台校验；缓存只用于显示，严格沿用服务端 `crmScopeExpiresAt`，过期、权限拒绝或来源范围失效时清空，项目/节点写操作成功后失效，不保存详情、草稿或凭据。异步响应仍按完整 sessionId/用户/代理身份隔离，旧登录的响应不能更新新登录的页面。
- 总览复用同一用户的后台 CRM 同步与有效范围，统计由数据库聚合，最近项目、最近工单、待办和风险各最多返回 8 条轻量摘要；`taskTotal`/`alertTotal` 是当前可见个人范围的完整数量，不是摘要条数。待办优先展示最早到期的任务，风险摘要兼顾售前轮次临近到期/超时、售中售后超时节点、高优先级工单和异常项目。无有效 CRM 范围或来源失败时，仅展示仍可访问的本地服务，并明确提示 CRM 售前暂未计入；不以全零代替加载失败。同步期间沿用售前列表的渐进轮询，平时每 30 秒更新，失败后自动重试，不提供手动刷新按钮，离开页面停止轮询。
- CRM 可见 ID 与商城一样按 Auth 当前用户和操作者复用，并额外隔离能力、代理状态和终端；每个 HTTP 请求仍先经过 Auth 校验。默认新鲜期 300 秒（通过 `CRM_PROJECT_SOURCE_SYNC_INTERVAL_SECONDS` 调整），随后后台刷新，旧结果最多保留一个刷新窗口（默认总计 600 秒），有效期从 CRM 响应完整验证时起算，不因流程导入耗时或刷新失败延长。生产沿用平台 Redis，进程共享缓存锁；开发无 Redis 时使用进程内缓存，内存 SQLite 测试同步执行。显式刷新绕过短期失败缓存；403 清除该用户身份范围，不能被网络错误或旧导入结果覆盖；旧登录的 401 不撤销同一用户新登录的有效快照。响应的到期时间对应本次列表实际使用的范围，不借后台刚完成的新范围给旧列表续期。
- 后台同步一次读取已有项目，未变项目不逐条锁定/写入，变动项目按 100 条批量更新，新项目复用原工作流初始化。Redis 用户范围锁及 PostgreSQL advisory lock 防止并发重复导入；数据库锁只覆盖本地导入事务，不覆盖网络读取，不同用户可同时读取自己的来源范围。用户范围锁在来源读取及导入期间续期，进程意外退出后最多 90 秒释放，旧任务不能移除接替任务的锁。同步不重置节点，不覆盖历史项目信息记录、备注或附件，不恢复已删除的服务流程。详情和写操作继续实时通过 CRM 项目详情校验授权。
- 售后管理员仍需拥有 CRM 的商机读取权限（例如 CRM 的「商机只读」权限）。售前列表、详情、节点操作、附件和关联资源按当前有效身份检查 CRM 范围；代理不会继承操作者权限。CRM 无权限/不可用时显示明确错误，不降级为跨用户读取缓存。
- 售前列表同时展示当前账号可见的 CRM 项目及本地新增项目，搜索、筛选、统计和分页均涵盖两类来源；旧的本地售前测试记录保留原 ID、附件和历史，不自动匹配或删除。保留「新增售前项目」入口，新增记录不绑定或写回 CRM，本地项目信息可独立维护。CRM 暂不可用或没有 CRM 权限时，隐藏 CRM 来源并提示错误，本地售前仍可读取和维护。
- 售前、售中、售后项目列表及总览最近项目在数据库分页前按创建时间倒序、ID 倒序排列：CRM 来源严格使用 CRM 商机的原始 `createdAt`，本地项目使用本地创建时间；缺少有效 CRM 创建时间的来源项目排在有时间的项目后，不拿导入时间代替。同步快照保存并校验该字段，日期格式异常不参与「新」标记。管理端桌面项目名称旁仅对北京时间当天在 CRM 新建的项目显示「新」，次日自动移除；今天同步旧商机、修改服务节点、留痕或 CRM 后续更新均不算新。本地项目不标「新」。沿用列表/总览的现有刷新，不额外请求 CRM、不修改 CRM 数据或服务流程创建时间。
- 售前、售中及售后服务订单表头「搜索项目名称」使用 `nameSearch`，仅按名称做不区分大小写的包含匹配，并在数据库分页前按完全匹配、开头匹配、包含匹配排序；同等级沿用创建时间倒序、ID 倒序，清空搜索恢复原排序。URL 继续保存 `search` 作为页面搜索词；接口原有 `search/q` 综合搜索保持原契约，客户与负责人筛选仍独立叠加，CRM 权限范围不变。
- 服务奖励的奖品名称、项目名称、获得人员分别搜索；工单及反馈的标题、所属项目、节点、提交人以及工单处理人、反馈类型也各自筛选，条件可叠加。服务团队的姓名／手机号框只匹配姓名或手机号，区域、能力与认证状态使用各自筛选。
- 售前推进的每轮提交窗口提供「打开商城方案」。仅在打开窗口时调用 CRM「打开方案」同一正式接口 `GET /api/crm/opportunities/{sourceCrmId}/solution-products`，使用返回的 `projectDetailUrl`；CRM 校验当前会话的项目可见范围，商城负责项目/方案映射和目标页权限，不按项目名称猜测关联。仅接受商城 `/maijie-mall/#/opportunity/{id}/solution[/{solutionId}]` 路由，并归一到当前平台域名，避免平台域名别名导致会话丢失。普通浏览器打开新页，钉钉沿用既有工作台 AppLink，原提交窗口保留附件和备注。无权限、未关联、网络失败分别提示并支持重试；本地独立项目显示未关联原因，不查询或创建商城项目。
- 售前推进每轮提交旁提供「转发」，先保存当前草稿，再调用 Auth 正式 `GET /api/auth/dingtalk/jsapi_config` 为 `biz.util.share` 签名，由钉钉原生分享窗口选择联系人/群聊。卡片包含项目、节点和轮次标题，AppLink 打开原售前项目页并定位 `projectId/nodeKey/roundId`、弹出既有附件备注窗口；浏览器提供复制链接。固定 `roundId` 按需写入原轮次 JSON，删除后重新新增不会复用旧编号；转发不授予项目权限，也不进入等待/锁定/撤回/更换处理人流程，原推进方式保留。取消或发送失败不显示成功，准备链接不记录虚假的发送事件。新钉钉窗口没有 Cookie/本地会话时，仅对此类转发入口沿用 Auth 工作台免登，随后仍读取应用权限并检查 CRM 项目授权；拒绝/撤销登录不会静默绕过。首次权限校验完成前保留入口链接。
- 浏览器转发窗口复制的链接同样使用钉钉 AppLink（桌面 `targetDesktop=workbench`），不复制普通项目网页地址；接收人在钉钉聊天中点击后，进入对应项目和轮次。聊天卡片图标由售后前端静态路由 `/after-sales/round-share.png` 提供。
- 已完成/跳过节点的资料只读，仍支持查看、预览和下载；管理端人员配置、项目信息、费用备注、关联产品和流程结果选框均遵守节点状态。服务端草稿、版本提交、推进、产品更新、附件上传删除同步限制；售前历史轮次附件不能删除，方案附件上传携带当前轮次索引和固定编号。并列活动节点独立可编辑，显式节点回退仍沿用原流程。
- 管理端桌面售前详情顶部使用「节点详情 / 项目信息 / 版本与留痕」；项目信息集中展示费用、面积与项目等级。费用信息为整个售前项目共用的只读区域：预计费用读取 CRM 项目详情的 `amount`，与商城灰色预计金额的 `expected_amount` 同源；对外报价读取 CRM 正式 `GET /api/crm/opportunities/mall-amounts?opportunityId={sourceCrmId}` 返回的 `salespersonQuoteTotal`，实际费用读取同一记录的 `a1Total`，仅查询当前项目，不读取所有可见项目汇总。按 CRM 项目 ID 精确匹配，沿用商城对当前关联方案的项目汇总，不取自有产品 A1、不额外叠加辅助费用、不累加历史版本。仅打开项目信息页签时发起来源请求，按登录、有效用户、代理及应用能力隔离内存缓存：30 秒内复用已读结果，并合并同项目同来源的在途请求；超过新鲜期先显示最近金额并后台更新，超过 5 分钟不再使用旧值。页签可见时每 30 秒及重新聚焦按需校验，离开后停止轮询；不持久化费用，身份变化或来源拒绝访问时清空缓存。来源可独立失败及重试，空值不显示为 0，本地独立项目说明未关联且不发起来源查询；切换项目/登录身份丢弃过期响应。移动 Web 保留原费用页签，不新增面积、等级入口。原售前节点费用保留历史但不再编辑，节点草稿、版本及通过操作忽略节点费用和报价写入。售中/售后费用仍在当前节点下方的同级折叠区，沿用原自动保存、现场提交及只读规则。售前推进资料仍在各轮提交窗口查看，所有售前节点均不显示通用「交付资料」区块，仅已有普通补充附件时显示「节点补充附件」，切换节点时清空上一节点的附件展示。售中/售后的现场资料与审核在节点交付资料折叠区查看。「版本与留痕」汇总项目及全部节点记录，不随节点切换筛选，标明所属节点、操作人及代理身份；项目详情返回完整事件记录，不再截断到最近 100 条。列表接口仍不加载事件。
- 提交窗口的「通过」沿用当前售前节点推进和并行依赖；「新增一轮」必须填写原因，新轮成果附件为空，不继承上一轮，时间、备注独立填写，历史轮次保持原样。新轮可上传或确认移除本轮附件；对历史版本已继承的附件，移除时只删除当前轮引用，不删除历史文件，仅本轮使用的文件在事务提交后删除。`process` 的 `remove_attachment` 操作接收 `attachmentId` 并沿用权限、节点及版本校验，同时检查附件属于当前节点、提交分类和最新轮，记录移除留痕。仅最新轮次可处理，历史/已完成轮次只查看处理状态；`POST /api/after-sales/projects/{id}/nodes/{nodeKey}/rounds/{prepare-forward|process}` 在同一项目事务中检查管理端/CRM 权限、节点状态、轮次固定编号和 `expectedUpdatedAt`，过期内容/重复提交返回 409，已删除轮次返回 404。实际处理写入项目版本留痕（操作人/代理人、轮次、通过或新增原因）；不恢复旧的每轮结果审核字段，也不新增数据库表。已有轮次不自动补入或清除附件。
- 「新增一轮」的原因窗口支持选填多个任意类型附件，本次附件合计最多 200MB，沿用 API 的 201MB 请求上限。选择阶段仅保存在浏览器内，可移除或取消；图片和 PDF 在确认新增前即可通过缩略图、文件名或预览按钮本地预览，关闭预览保留原因及附件，Esc 仅关闭最上层预览；新增售前项目的原始附件沿用相同预览。关闭、切换项目/节点、离开模块及刷新均保护未提交草稿，提交中禁用重复操作。无附件继续使用 JSON；有附件时 `process` 使用 multipart，`payload` 为原 JSON、`reasonFiles` 为多个文件，仅 `add_round` 接受文件。权限、轮次和版本验证后，在同一数据库事务中创建私有附件与新轮，失败清理已写文件。原因附件沿用节点的 `scheme_submission` 存储分类，但使用新轮的 `reasonAttachmentIds` 单独关联，提交窗口独立展示并复用图片/PDF 预览与下载，不混入成果 `attachmentIds`、不继承到下一轮或售中成果资料。保存后原因附件只读，草稿/版本/推进不能伪造或改写附件引用；删除无成果附件的最后一轮时，清理该轮独有的原因附件并在事务提交后删除文件，历史轮次不变。
- 操作列只向本地项目提供删除按钮；服务端 DELETE 同样拒绝 CRM 来源项目（`403 CRM_PROJECT_DELETE_FORBIDDEN`），即使绕过界面调用也不能删除。售中/售后的本地新增、删除与微信任务流程保持原业务规则。
- CRM 删除或列表中不再可见的项目不会导致本地流程或附件被删除、取消或完成。记录保留在数据库，读取/操作仍需要 CRM 当前授权；不能用一次列表缺失推断来源已删除。已有同步项目当前未达到「方案渗透」时，从售前列表、总览及关联列表中隐藏，保留原节点、轮次、人员、附件、留痕和排序时间；阶段满足条件后复用原项目。阶段门槛在数据库分页、阶段筛选选项及总览聚合前统一应用，CRM 可见范围、后台同步和分页缓存机制沿用原规则。

- 售前「项目信息」页签中的项目总面积与设计面积（㎡）均选填，允许 0，最多两位小数；项目等级单选「常规，金额小 / 常规，金额大 / 特殊，金额小 / 特殊，金额大 / 重要，金额小 / 重要，金额大」，紧急程度单选「一般 / 紧急 / 非常紧急」，均可清空，复用管理端表单下拉组件，不增加「未填写」选项。项目属性中增加「预计招标时间」，复用日期控件，选填、可清空，仅填写年月日，不限制与节点排期的先后关系。保存在项目级 `businessData.projectInfo.totalArea/designArea/projectLevel/urgency/expectedBidAt`，统计分析明细直接读取。填写后自动保存，不另设手动保存按钮或常驻保存提示；切换页签、节点、项目或关闭详情时先保存，失败保留草稿并阻止离开，支持重试或确认放弃后重新读取。沿用项目管理与 CRM 实时可见权限，业务员、服务管理员、系统管理员可维护；不受当前选中历史节点的只读状态影响。`PATCH /api/after-sales/projects/{id}` 的 `presalesProjectInfo: {totalArea, designArea, projectLevel, urgency, expectedBidAt}` 仅接收这些字段，面积清空传 `null`，其余清空传空字符串，日期为有效的 `YYYY-MM-DD`，必须带 `expectedDraftVersion`；服务器在项目锁内验证版本、数值、选项和日期，仅合并实际改变的字段，保留其他项目资料及历史节点记录，有实际变化时记录项目留痕，空值及重复保存不增加记录。旧客户端省略 `urgency` 或 `expectedBidAt` 时保留其原值；旧 `presalesAreas` 参数继续兼容且不修改等级、紧急程度和日期。立项资料编辑与 CRM 同步保留项目面积、等级、紧急程度和预计招标时间。不将 CRM 投标时间复制或回填为本地预计招标时间。无数据库迁移，移动 Web、小程序和售中/售后不增加维护入口。
- 「项目信息」页签可上传、预览、下载与确认删除项目需求文档，复用私有附件与图片/PDF 预览组件；上传后即时显示，无需另行保存。新文档使用 `presales_project` 目标类型和项目 ID，分类仅允许 `general`，沿用项目维护权限与 CRM 实时权限，不受当前所选历史节点限制，已删除项目禁止写入。列表同时包含原前期立项节点的普通附件，保留其原位置和历史只读/删除限制，不移动或复制历史文件。统计分析按相同口径合计文档数量、按项目预览，并从全部统计视图删除「备注」列（原数据保留）；售中「售前资料」也可读取新文档。上传/删除处理中保护外层离开路径，删除失败保留确认窗口并允许重试。`0030_alter_privateattachment_target_type` 仅新增附件目标枚举，不迁移已有业务数据；手机端不增加入口。
- 项目及节点草稿重复保存相同内容不写入更新时间或操作人，项目资料无变化不新增「更新项目资料」留痕；面积的等值数字格式、可选面积/等级的缺省与空值视为相同，0 与未填写仍有区别。权限、版本冲突及历史只读校验照常执行，真实修改、明确提交版本、推进节点和附件操作继续留痕。CRM 自动导入仅初始化服务流程，不记录「创建服务项目」；旧 CRM 导入的同类创建事件保留在库中但不展示，本地手工新增项目继续记录创建事件。
