# 表单设计（平台接入版）

App ID：`form-designer`。由 `D:/Desktop/表单设计/` 的现有业务源码迁移，保留 Vue 3 + TypeScript 表单设计、条件流程、审批/执行和数据管理，后端改为 Django + PostgreSQL。原目录及其 MySQL/SQLite 数据未修改。

## 平台边界

- 页面：`/form-designer/`；业务 API：`/api/form-designer/`。
- 应用清单声明独立前端、后端、数据库、网络、数据卷和 Secret。
- 后端只连接 `form_designer_db`，使用独立低权限账号 `form_designer_user`。数据库结构由 Django migrations 管理。
- Auth 是身份、会话和组织目录的权威来源。App 不维护密码、会话或组织角色，不直接访问 Auth 数据库。
- 前端使用 `@platform-ui` 的会话、请求、顶栏、侧栏、详情抽屉和遮罩组件；后端 `platform.py` 适配共享 `platform_auth`。
- Auth token 仅由 Auth 管理。App 不签发 token，不写入/删除 `mj_auth_token`，浏览器不访问 Auth 内部接口。
- 当前有效用户使用 Auth `userId`，实际操作人单独审计。代理目标不继承操作者的管理员权限。
- 页面级访问成员和是否允许发起由后端校验；数据管理统一要求应用管理员，不因浏览器传入角色而放宽。

## 流程申请分类

工作台提供销售、商务、售前、采购、行政、人事、财务、产品八个预设分类，并保留“全部流程”和已有分类。流程设计页的“分类”通过下拉框选择，发布后在工作台生效。分类下只展示当前用户可访问的已发布流程；空分类不会生成示例申请。桌面采用四列图标卡片，窄屏自动调整列数，分类栏支持左右滚动和键盘切换。

## 统一审批首页

管理员和普通用户共用审批首页，左侧只保留“审批首页”。首页显示当前登录人的待处理、已退回、我发起的、我已处理数量；进入首页默认展开“待我处理”，待办可直接打开审批/执行详情；首页不再显示“最近发起”。“发起审批”保留预设及已有分类。

首页“发起审批”区域的“更多”进入页面管理工作台；“待我处理”的“更多”进入流程状态页并默认显示“待我处理”。管理员可从工作台左侧新建审批，或进入选中流程的表单设计、流程配置和数据管理。从“更多”进入编辑后，顶部只提供“返回更多”作为返回入口，回到原工作台并保留选中的流程、搜索、筛选及页码，同时刷新数据；表单设计、流程设计及数据管理间切换后仍可返回。编辑时不显示“返回审批首页”，回到更多后可再返回首页；内部设计导航保留。

点击“返回更多”时若表单或流程有未保存修改，使用“是否放弃修改”确认框：“继续编辑”保留当前内容；“确认放弃”读取已保存版本后返回，读取失败保留编辑及提示，可重试。保存或发布过程中暂不返回，避免中断操作。工作台通过Vue缓存保留本次页面状态；刷新浏览器后重新进入。

## 发起人撤回申请

在审批首页的“我发起的”或“最近发起”打开申请详情，或者从“更多 → 我发起的 → 查看详情”进入，点击底部“撤回申请”，可选填撤回原因并确认。此操作独立于审批节点的按钮配置，不需要发起人同时担任当前审批人。

仅当前有效 Auth 用户为原发起人、且流程处于 `pending`（审批／执行处理中）或 `pending_assignment`（待分配）时允许撤回。管理员不能代替其他发起人撤回；Auth 代理按有效用户的发起人身份授权，同时记录实际操作者。已完成、已拒绝、已退回或已撤回的流程返回 409，页面刷新最新状态。

撤回保留申请记录、表单内容和已有审批／执行决定，将当前及未来的 `pending/waiting/unassigned` 任务取消，待办随之移除；已完成节点及已完成的处理人进度不改动。流程显示“已撤回”，详情保留撤回人、时间和原因。撤回不会倒退已完成的业务操作。

新增 `POST /api/form-designer/workflow-runs/{run_id}/recall`，请求体为 `{ "comment": "可选原因，最多2000字" }`。服务端按 Auth 稳定 userId 校验身份，使用与任务处理相同的 PostgreSQL 行锁；撤回与审批提交按锁顺序处理，终态不能被后到操作覆盖。撤回写入与业务审计同事务，失败回滚；响应只返回操作状态和撤回信息，申请详情继续通过原有读取权限接口获取。无数据库模型变更。

## 应用业务权限

| 权限 | 能力 |
| --- | --- |
| user | 发起获准的流程，处理分配给自己的任务，查看自己的申请和处理记录 |
| designer | 包含 user；配置和发布表单、流程；不能配置应用权限或管理全部业务数据 |
| admin | 应用内管理能力，保留后端权限配置授权和业务数据管理 |

平台最高权限只消费 Auth 返回的 `canUseSystemAdmin=true`。普通成员默认无权进入，由应用管理员授权。权限规则支持部门、部门及下级、直接人员、排除人员，按照稳定 `deptId/userId` 保存。权限配置接口保存需同时提交 `revision/orgRevision`；组织或配置变化时返回 409。页面已移除“应用权限”和工作台“权限设置”入口，应用外壳不再挂载权限编辑页；既有授权规则及后台身份、角色和数据访问校验继续生效。分类主管选择仍复用受保护的组织目录接口。

权限接口：`GET/POST permissions`、`GET permissions/directory`。所有路径均带 `/api/form-designer/` 前缀。

以仓库的 `ai写代码前必读/` 标准 App、Auth、组织权限和页面规范为依据。当前提供的仓库缺少 `skills/mj-platform-standards/SKILL.md`、`packages/platform-ui`、`packages/platform-backend` 和标准生成/验包工具，因此本目录按文档组装和迁移，未声称执行了原版生成器或通过原版 SDK 联调。

1. 放入 `apps/form-designer/`，提供真实的共享 `platform-ui` 和 `platform_auth`。核对共享组件、会话和中间件版本契约。

4. 在平台测试环境运行迁移、前端生产构建，以及真实 Cookie 登录、代理切换、退出、目录分页和权限验收。
5. 按负责人指定的可信 baseline，执行平台原版 `package_app.py/import_app.py`，生成并校验正式交付包。

本次仅完成本地接入验证；没有连接或发布到公司正式系统。Dockerfile 和清单用于后续标准交付，本次本地运行未使用 Docker。

## 审批填写页

点击审批首页分类中的流程卡片，使用共享 `PlatformDetailDrawer` 打开填写页：顶部显示“发起＋表单名称”，表单按照已发布设计的字段顺序与整行／半行配置排版，半行字段并排、整行字段独占一行；窄屏（不超过 700px）自动单列。日期范围使用开始／结束日期，底部保留固定的“保存草稿／提交审批”操作栏。填写页不展示预计审批流程，也不随填写内容调用预览接口；提交成功后，在结果抽屉展示服务端实际生成的审批节点、处理人及当前状态。修改设计后，重新发布关联流程才会更新填写页。字段仍来自已发布的表单快照，遵守隐藏与只读权限；成员字段使用 Auth 稳定用户 ID。

草稿按当前 Auth 账号和流程 ID 保存在本机浏览器中。填写页只保留“保存草稿”和“提交审批”，不再提供草稿历史。每次保存覆盖上一份草稿，再次进入或刷新填写页时自动恢复最近一次保存的内容；提交成功后也保留该草稿，直到下次保存覆盖。未保存修改不会覆盖已保存内容，关闭时仍提示确认。

旧单份草稿和旧历史格式均可读取；旧历史取最近一次保存的内容，下一次保存时写为单份格式。流程更新后按字段ID和类型恢复兼容内容，新字段使用当前默认值，失效选项和人员不回填；隐藏字段不恢复，只读字段始终使用当前默认值。草稿未接入服务端同步，更换浏览器或清除存储后不能恢复；保存失败保留原草稿，读取失败不覆盖原记录。

`POST /api/form-designer/workflows/{workflow_id}/preview` 根据已发布流程和当前填写内容计算预计节点及处理人，不创建申请、待办或业务审计记录，也不向普通用户下发完整流程配置。该接口保留供兼容使用，当前填写页不调用；实际流程以提交时计算为准。服务端同时校验表单访问权限、提交权限、只读／隐藏字段和日期范围。提交成功提示也使用共享抽屉。

## 流程分类、记录和生命周期

“发起审批 → 更多”的左侧分类下展示具体流程，点击后按 workflowId 查询该流程的申请记录；普通成员在此处仅查看本人发起的申请记录；当前待办及已处理任务通过流程状态页查看。管理员有“编辑流程表单”“停用／启用流程”“删除流程”操作。

停用阻止新申请和预览，保留记录与待办，重新发布不会自动启用。删除采用逻辑删除：从可用分类和发起入口移除，禁止编辑、发布和新申请，保留表单、历史快照及正在处理的审批；管理员在“发起审批 → 更多 → 流程回收站”查看已删除流程，支持按名称／分类搜索、分页、查看历史记录及恢复。恢复后返回原分类，保留删除前的发布／停用状态；草稿恢复后仍需发布。删除后的 ID 保留，不能通过旧草稿或重建同 ID 复活，只能由管理员通过恢复操作移出回收站。

普通流程列表默认排除已删除流程；回收站使用 `GET workflows?recycle=true`，仅管理员可读。管理接口为 `POST workflows/{id}/disable`、`POST workflows/{id}/enable`、`DELETE workflows/{id}` 和 `POST workflows/{id}/restore`，均带 `/api/form-designer/` 前缀，仅应用管理员可用，代理按有效用户权限检查。状态存于既有流程 JSON，无模型变更；保存、发布、启停、删除、恢复和发起在 PostgreSQL 事务中按流程序列化，状态操作与审计同事务提交。浏览器验收使用路由替身，后端测试使用独立测试数据库。

审批首页保留平台一级导航。“发起审批 → 更多”“最近发起 → 更多”、新建和编辑流程／表单以及其他管理页面隐藏最左侧一级导航，内容使用完整宽度；手机端同步隐藏“审批首页”导航条并释放空间。工作台内部分类导航、顶部账号栏和返回审批首页入口保留，返回首页后一级导航恢复。页面状态通过Vue组件事件传递，不修改共享平台组件。

流程操作栏将标题／分类与状态／操作分行，空间不足时按组换行，按钮文字保持单行。新建为普通按钮，保存为浅蓝按钮，发布为蓝色主按钮。桌面按钮高36px、手机端40px，保留键盘焦点；保存和发布显示加载图标及文字，并禁用重复操作。原保存、先保存后发布、失败重试和未保存离开确认继续生效。

## 分类主管与审批节点的直属主管

创建工作流弹窗和流程设计页顶部均通过下拉框选择流程分类，选项包含八个预设分类、常用流程及已有流程的草稿／已发布分类。两处均已移除“自定义分类…”选项和输入框；已有分类及流程数据继续保留。设计页切换分类后需保存并发布，首页分类和之后申请的主管分配按发布版本生效。

管理员在“发起审批 → 更多”左侧流程分类行点击“主管”，为该分类下所有流程选择主管；设置入口位于分类旁，不在记录工具栏。支持人员搜索、连续多选、调整顺序和清空。人员来自Auth组织目录，配置保存稳定userId，存于本App的`CategorySupervisorState`，由迁移`0002_categorysupervisorstate`创建。草稿和停用流程可设置，回收站及已删除流程不显示该入口。

审批节点沿用“直属主管”选项：提交时根据流程已发布版本的分类读取分类主管，按节点原有审批模式生成任务；默认依次审批。保存分类主管直接影响之后发起的申请，不改变已提交任务的处理人、进度或授权。未设置分类或主管已不可用时，发布及新申请返回明确错误，不创建部分申请记录；指定成员节点仍使用节点选定人员。执行节点原有组织主管规则保持。

`GET /api/form-designer/category-supervisors`读取配置，`POST`按单个分类更新`{category, supervisorUserIds, revision, orgRevision}`，均仅应用管理员可用。目录复用`permissions/directory`；服务端校验Auth组织版本和配置版本，保存及审计同事务提交，409后前端重读并要求重新确认。设置主管不授予设计、流程管理或应用管理员权限；审批任务通过原有待办、审批动作和数据权限接口处理。

## 条件分支演示流程

本地已安装并发布5个“【示例】”流程：设备采购、费用报销、员工请假、行政用印和销售合同，分别覆盖金额阈值、天数、类型以及串联条件分支。每个示例有独立表单和默认填写内容，不预先创建申请记录；演示处理人使用指定本地账号，不改动分类主管。打开审批首页的对应分类即可发起，管理员可从“更多 → 编辑流程表单 → 流程设计”查看分支。

详细规则、演示账号分工及复现方式见[条件分支演示说明](examples/README.md)。定义保存于`examples/branch-demos.json`，应用启动不会自动导入；辅助安装工具只创建不存在的ID，已有或回收站内同ID均跳过，不覆盖用户后续编辑。这些定义及本地Auth账号用于本地演示，不代表公司正式环境已接入。


## 表单名称编辑

表单设计、预览和审批填写页只显示表单名称，不再显示表单顶部说明。画布名称支持直接修改；右上“编辑名称”可聚焦属性区的“表单名称”，两处同步，点击“保存名称”沿用原保存接口。正式申请使用的新名称需重新发布关联流程。已有说明数据保留兼容，但页面不提供说明显示或编辑入口；表单内独立的业务字段保持原样。

## 流程状态更多的分类筛选

流程状态页的分类下拉与发起审批共用`publishedWorkflowCategories`：固定八个标准分类，再补充当前已发布、未停用且未删除流程的发布分类（无分类归常用）。不从历史申请提取选项，旧“功能测试”“本地接入验证”不再因历史记录出现在下拉框；无申请的标准分类仍可选择并显示空记录。草稿分类改动不会影响下拉，发布后刷新生效。

历史申请保留发起时分类，仍可在“全部分类”查看和搜索，不迁移或删除旧数据。刷新同时独立读取记录与流程目录；分类读取失败保留原选项与选择并提示重试，记录读取失败保留原列表。成功刷新后若所选分类已失效，自动退回全部分类并重置分页。四个个人范围及状态、标题等筛选继续组合使用；抄送业务仍未接入真实数据。


## 员工申请记录隔离

“发起审批 → 更多”的普通成员记录列表仅显示本人发起的申请，标签为“我的申请”；审批主管也遵守该规则。`GET approval-records`默认`scope=applications`，服务端根据Auth有效userId和历史申请发起人ID筛选，不能通过姓名、客户端userId或其他参数扩大范围。管理员保留全部申请的管理权限，代理身份使用被代理人的权限。

“最近发起 → 更多”显式读取`scope=personal`：我发起的仍仅本人申请；待我处理仅当前可操作任务；我已处理仅本人实际作出处理决定的记录。尚未轮到的后续审批人或同节点顺序审批成员不能提前读取他人申请摘要或详情；当前处理人及已处理人可通过任务入口按字段权限查看必要内容。无关用户猜测详情ID返回404，直接使用全部业务记录接口仍返回403。本人查看关闭／成员访问限制继续生效，历史数据不迁移不删除。
