# 统一组织权限页面与接口规范

本文档规定 CRM、线缆商城以及后续 ERP 等 App 使用 Auth 部门和员工分配业务权限时的统一页面、前端状态和后端接口契约。凡是出现“按部门授权”或“按员工授权”，开发前必须阅读本文和 [Auth 内部接口说明](./auth内部接口说明.md)。

## 2. 页面必须表达三层关系

权限页不能只展示数据库里的规则条数，必须把下面三层关系呈现清楚：

```text
权限项
  └─ 权限来源
       ├─ 部门（可选是否包含子部门）
       └─ 人员（直接授权）
            └─ 实际生效成员（来源合并并扣除排除人员）
```

桌面页面标准布局：

```text
左栏：权限项列表
  - 权限名称和说明
  - 生效人数
  - 来源数量

右栏：当前权限详情
  - 部门来源卡片
  - 人员来源卡片
  - 实际生效成员表格
  - 姓名、所在部门、权限来源、状态、操作
```

这里的“人数”是最终生效人数，不是权限规则条数。系统管理员通过 Auth 的 `canUseSystemAdmin` 自动获得当前 App 的最高权限，不需要依赖业务权限规则；但系统管理员仍可出现在人员目录中，也允许预先配置普通业务权限。

## 3. 部门和人员选择器

### 3.1 部门选择器

部门必须显示为可展开树，不能通过在名称前拼全角空格伪造层级。每一行至少包含：

```text
多选框
展开/收起图标
部门名称
deptId
“包含子部门”多选框
部门人数
```

规则：

1. 选择部门但不选择“包含子部门”时，只授权该部门的直接成员。
2. 选择“包含子部门”时，保存为 `scopeType=departmentSub`，授权该部门及全部后代部门成员。
3. 上级已经包含子部门时，下级显示为被上级强制选中，不重复保存下级规则。
4. 开启“包含子部门”时，删除该权限项下已有的后代部门重复来源。
5. 搜索命中子部门时保留祖先路径；搜索时自动展开匹配路径。
6. 搜索字段包含名称、deptId、`pinyinInitials`、`departmentPathText`。

部门树标准化和搜索的核心源码：

```js
function normalizeDepartmentTree(nodes = [], depth = 0) {
  return nodes.map((node) => {
    const id = String(node.deptId ?? node.dept_id ?? node.id ?? "").trim();
    if (!id) return null;
    const children = normalizeDepartmentTree(node.children || [], depth + 1);
    return {
      id,
      name: String(node.name || id),
      depth,
      parentId: String(node.parentDeptId ?? node.parent_dept_id ?? ""),
      pinyinInitials: String(node.pinyinInitials ?? "").toLowerCase(),
      departmentPathText: String(node.departmentPathText ?? ""),
      childIds: children.flatMap((child) => [child.id, ...child.childIds]),
      children,
    };
  }).filter(Boolean);
}

function filterDepartmentTree(nodes, keyword) {
  if (!keyword) return nodes;
  return nodes.map((node) => {
    const children = filterDepartmentTree(node.children || [], keyword);
    const text = [node.name, node.id, node.pinyinInitials, node.departmentPathText]
      .filter(Boolean).join(" ").toLowerCase();
    if (text.includes(keyword)) return node;
    return children.length ? { ...node, children } : null;
  }).filter(Boolean);
}
```

### 3.2 人员选择器

人员选择器必须支持连续多选，不能每选一人就关闭。每行显示姓名、userId、所在部门和选中状态；搜索字段包含姓名、userId、人员拼音首字母、部门名称、部门编号和部门拼音首字母。

标准化核心源码：

```js
function normalizeEmployee(item) {
  const id = String(item.userId ?? item.user_id ?? item.id ?? "").trim();
  return {
    id,
    name: String(item.name ?? item.rawName ?? id),
    avatarUrl: String(item.avatarUrl ?? item.avatar_url ?? ""),
    pinyinInitials: String(item.pinyinInitials ?? "").toLowerCase(),
    departments: (item.departments || []).map((department) => ({
      id: String(department.deptId ?? department.id ?? ""),
      name: String(department.name ?? ""),
      pinyinInitials: String(department.pinyinInitials ?? "").toLowerCase(),
      departmentPathText: String(department.departmentPathText ?? ""),
    })),
  };
}
```

## 4. 权限规则和实际成员逻辑

统一范围类型：

```text
department       仅指定部门直接成员
departmentSub    指定部门及全部子部门成员
employee         直接授权人员
excludedEmployee 从该权限的部门来源结果中排除人员
```

对某个权限项 `permission`，实际成员集合必须按下面的集合关系计算：

```text
effectiveMembers =
  (directEmployeeMembers ∪ departmentMembers ∪ departmentSubtreeMembers)
  - excludedEmployeeMembers
```

前端成员表核心源码：

```js
function memberRows(permission, rules, employees, departmentById) {
  const departmentIds = new Set();
  const directEmployeeIds = new Set();
  const excludedEmployeeIds = new Set();

  rules.filter((rule) => rule.permission === permission).forEach((rule) => {
    if (rule.scopeType === "employee") directEmployeeIds.add(String(rule.targetId));
    if (rule.scopeType === "excludedEmployee") excludedEmployeeIds.add(String(rule.targetId));
    if (["department", "departmentSub"].includes(rule.scopeType)) {
      const department = departmentById.get(String(rule.targetId));
      departmentIds.add(String(rule.targetId));
      if (rule.scopeType === "departmentSub") {
        (department?.childIds || []).forEach((id) => departmentIds.add(String(id)));
      }
    }
  });

  return employees.filter((employee) => {
    const includedByEmployee = directEmployeeIds.has(employee.id);
    const includedByDepartment = employee.departments
      .some((department) => departmentIds.has(department.id));
    return (includedByEmployee || includedByDepartment)
      && !excludedEmployeeIds.has(employee.id);
  });
}
```

“踢掉”人员时：

```text
人员只有 employee 直接来源：删除 employee 规则。
人员由部门来源带入：删除同权限的 employee 规则，并新增 excludedEmployee 规则。
人员同时有直接和部门来源：删除 employee，并新增 excludedEmployee。
恢复人员：删除 excludedEmployee 规则。
```

后端必须重复执行相同语义，不能信任前端算出的成员表。后端判断 `departmentSub` 时，应从员工所属部门沿 `parentDeptId` 向上查祖先；如果规则目标在祖先集合中即命中。`excludedEmployee` 按权限项生效，只排除同一个 `permission`。

## 5. 目录与保存接口契约

浏览器只能调用本 App 后端，不能直接调用 Auth `/api/internal/*`。App 后端用自己的内部服务凭据读取一致的 Auth 组织快照。

### GET 权限目录

```json
{
  "departments": [],
  "employees": [],
  "roles": [],
  "directorySource": "auth",
  "orgRevision": 3
}
```

要求：

```text
departments 是树结构。
employees 只给页面可选择的在职人员，并带 departments。
目录的所有分页必须来自同一个 orgRevision。
App 可以物化一份本地快照做授权，但 Auth 才是组织主数据源。
```

### GET 权限配置

```json
{
  "items": [],
  "revision": "1"
}
```

### POST 保存权限

```json
{
  "items": [
    {
      "permission": "user",
      "scopeType": "departmentSub",
      "targetId": "94343259",
      "targetName": "研发中心",
      "sortOrder": 0
    }
  ],
  "revision": "1",
  "orgRevision": "3"
}
```

前端 revision 保存源码：

```js
let permissionRevision = "";
let authOrgRevision = "";

async function loadPermissionPage() {
  const [permissions, directory] = await Promise.all([
    apiGet("/api/example/permissions"),
    apiGet("/api/example/permissions/directory"),
  ]);
  permissionRevision = String(permissions.revision || "");
  authOrgRevision = String(directory.orgRevision ?? "");
}

async function savePermissions(items) {
  const data = await apiPost("/api/example/permissions", {
    items,
    revision: permissionRevision,
    orgRevision: authOrgRevision,
  });
  permissionRevision = String(data.revision || "");
  authOrgRevision = String(data.orgRevision ?? authOrgRevision);
}
```

后端保存顺序必须是：

```text
1. 确认当前请求具有本 App 管理权限。
2. 强制刷新一次 Auth 组织快照。
3. 对比请求 orgRevision；不一致返回 409 ORG_REVISION_CONFLICT。
4. 开启数据库事务并锁定配置 revision。
5. 对比请求 revision；不一致返回 409 REVISION_CONFLICT。
6. 校验所有部门仍存在、所有人员仍在职。
7. 替换规则并递增 revision。
8. 返回新的 revision 和 orgRevision。
```

发生 409 后，前端必须重新读取目录和权限配置，提示用户重新确认，不得使用旧数据自动重试保存。

## 6. 禁止实现

```text
禁止用全角空格拼接部门名来伪造树。
禁止只显示部门/人员规则条数而不显示实际生效成员。
禁止选择一项后自动关闭多选弹窗。
禁止把 Auth 内部组织接口暴露给浏览器或网关。
禁止业务 App 直连 Auth 数据库。
禁止只提交 items 而不提交 revision 和 orgRevision。
禁止前端自行判断 FULL_ACCESS_USER_IDS。
禁止从人员选择器隐藏 Auth 系统管理员。
禁止把部门名称或人员姓名当稳定主键，必须保存 deptId/userId。
```

## 7. 最低测试清单

```text
部门树可展开、收起和搜索，搜索子部门时保留祖先。
department 不包含子部门成员。
departmentSub 包含全部后代部门成员。
直接 employee 与部门来源合并后不重复显示。
excludedEmployee 只排除同权限项，恢复后重新生效。
组织版本变化返回 409，权限版本变化返回 409。
目录中的离职人员不能保存为新规则。
canUseSystemAdmin=true 时拥有 App 最高权限；代理状态不继承操作者能力，但白名单目标保留自己的系统管理员能力。
前端生产构建通过，后端权限契约测试通过。
```
