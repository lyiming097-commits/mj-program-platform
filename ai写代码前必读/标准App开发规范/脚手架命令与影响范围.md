# 脚手架命令与影响范围

本文是标准 App 脚手架的命令手册，供开发者和服务器管理员在执行命令前确认：命令做什么、会写哪些路径、是否修改源码、是否操作 Docker、是否修改数据库。

第一次开发 App 时，还要同时阅读：

1. [基础目录结构](./基础目录结构.md)
2. [开发与部署流程](./开发与部署流程.md)
3. [App 协作开发与交付手册](../../docs/APP_COLLABORATION.md)

## 一、先记住这些名称

下文统一用 `erp` 作为示例 App ID。实际使用时，把 `erp` 换成平台负责人分配的唯一 App ID。

所有相对路径命令都应在各自机器的仓库根目录执行。生产服务器当前示例是：

```text
/usr/local/mj_program_platform/
```

开发者电脑使用自己 `git clone` 得到的仓库根目录，不要求也通常不会是上面的 Linux 路径。例如 Windows 可能是 `D:\work\mj_program_platform\`。

两种环境文件不要混用：

```text
local.env.docker    开发者电脑的本地环境
server.env.docker   生产服务器环境
```

目录的性质不同：

| 路径 | 用途 | 是否应提交 Git |
| --- | --- | --- |
| `apps/erp/` | ERP 的源码、依赖、migration 和 manifest | 是 |
| `secrets/apps/erp/` | ERP 的真实密码和内部服务密钥 | 否 |
| `.runtime/` | 自动生成的 Compose、网关、注册表、锁、回执和旧源码备份 | 否 |
| `.local/venvs/erp/` | 开发者本地 Python 虚拟环境 | 否 |
| `apps/erp/frontend/node_modules/` | 开发者本地前端依赖 | 否 |
| `apps/erp/frontend/dist/` | 前端本地构建产物 | 否 |
| `export/` | 开发者交付的 App ZIP | 否 |
| `backups/apps/erp/` | 服务器数据库备份 | 否 |

当前标准脚手架的后端是 Python + Django，数据库是 PostgreSQL，前端是 Vue。普通 App 必须沿用这个标准运行结构；换后端语言或自定义 Docker/Compose 不属于普通 App 开发，需要平台负责人单独设计和审查。

`apps/starter-app/` 既是平台中已登记的示例 App，也是 `new_app.py` 的受控页面和业务蓝本。生成器会读取其中指定的前后端源码并参数化 App ID、Python 模块、API 路径、表名和显示名称；Docker、Secret、网络和数据库资源仍由 `platform_runtime/scaffold.py` 安全生成。不要删除或随意改名 `starter-app`。修改蓝本只影响以后生成的新 App，已生成 App 不会自动同步；蓝本变化必须连同 `platform_runtime/scaffold.py`、`platform_runtime/templates/` 和脚手架测试一起审查、测试和发布。

## 二、最常用命令总览

| 操作 | 推荐命令 | 改 App 源码 | 改 Docker | 改数据库 |
| --- | --- | --- | --- | --- |
| 开发者创建骨架 | `python3 scripts/new_app.py erp --no-deploy --yes` | 是，新建 | 否 | 否 |
| 检查 manifest | `python3 scripts/appctl.py check --skip-secrets` | 否 | 否 | 否 |
| 本地部署一个 App | `scripts/app-deploy.sh erp local.env.docker` | 否 | 是 | 是，执行 migration |
| 开发者打包 | `python3 scripts/package_app.py erp --base <基准>` | 否 | 否 | 否 |
| 服务器只验包 | `python3 scripts/import_app.py <ZIP> ...` | 否 | 否 | 否 |
| 服务器安装新 App | `python3 scripts/import_app.py <ZIP> --install --deploy ...` | 是，新建 | 是 | 是 |
| 服务器更新已有 App | `python3 scripts/import_app.py <ZIP> --install --replace --deploy ...` | 是，替换 | 是 | 是 |
| 备份一个 App 数据库 | `python3 scripts/backup_app_db.py erp ...` | 否 | 不重建容器 | 否，只读取数据库 |
| 恢复一个 App 数据库 | `python3 scripts/restore_app_db.py erp <dump> --restore --yes ...` | 否 | 停止并重启后端 | 是，按归档清理并恢复对象 |

表中的“改数据库”指生产或本地部署数据库。Django 测试自己创建的临时测试库不算生产数据库。

## 三、创建标准 App

### 3.1 开发者只创建骨架，不部署

推荐命令：

```bash
python3 scripts/new_app.py erp \
  --name "ERP" \
  --description "企业资源管理" \
  --icon BriefcaseBusiness \
  --order 100 \
  --no-deploy \
  --yes
```

作用：

- 创建并校验标准 App 目录。
- 为新 App 生成缺少的 Secret。
- 校验新 App 加入后，全部 App 的 manifest、路由、网络和 Compose 模型是否冲突。
- 目标 `apps/erp/` 已存在时直接失败，不会覆盖。

会写入：

```text
apps/erp/
secrets/apps/erp/
.runtime/platform-app-mutation.lock
```

标准骨架通常会创建这些 Secret：

```text
secrets/apps/erp/django.secret
secrets/apps/erp/database-password.secret
secrets/apps/erp/auth-introspection.secret
```

影响范围：

| 项目 | 结论 |
| --- | --- |
| 源码 | 新建 `apps/erp/` |
| Docker | 不构建镜像，不创建容器、网络或数据卷 |
| 数据库 | 不创建、不连接、不迁移数据库 |
| 适用位置 | 开发者电脑；服务器只在确实要直接开发时使用 |

注意：`--no-deploy` 不是“只写 `apps/erp/`”。它仍会创建 `secrets/apps/erp/`，并使用 `.runtime/platform-app-mutation.lock` 防止多个安装或部署任务同时修改平台。

如果省略参数直接运行：

```bash
python3 scripts/new_app.py erp
```

交互终端会询问名称、说明和是否部署；默认选择“不部署”。为了让操作记录明确，团队协作时建议写全 `--no-deploy` 或 `--deploy`。

`new_app.py` 支持的创建参数：

| 参数 | 作用 |
| --- | --- |
| `--name NAME` | 门户显示名称，省略时默认使用 App ID |
| `--description TEXT` | 门户说明 |
| `--icon ICON` | Lucide 图标名称 |
| `--order NUMBER` | 门户排序数字 |
| `--no-deploy` | 只创建、生成 Secret 和校验 |
| `--deploy` | 创建后立即部署 |
| `--env-file FILE` | 部署使用的环境文件 |
| `--yes` | 跳过最后一次交互确认，不代表跳过校验 |

### 3.2 创建后立即部署

开发者电脑：

```bash
python3 scripts/new_app.py erp \
  --name "ERP" \
  --env-file local.env.docker \
  --deploy \
  --yes
```

生产服务器：

```bash
python3 scripts/new_app.py erp \
  --name "ERP" \
  --env-file server.env.docker \
  --deploy \
  --yes
```

除 3.1 的路径外，还会：

- 生成 `.runtime/apps-registry.json`、`.runtime/compose.apps.yaml` 和 `.runtime/nginx.conf`。
- 在 `.runtime/app-deploy.erp.*` 建立临时部署目录，成功后清理。
- 构建 ERP 镜像，创建或重建 ERP 容器、网络和数据卷。
- 重建 Auth 后端、网关和 Portal 后端，使入口、路由和内部服务凭据生效。
- 启动后端时自动执行 Django migration，因此会创建或修改 ERP 数据库结构。

`--deploy` 没写 `--env-file` 时默认使用 `server.env.docker`。为防止在开发者电脑误用生产配置，实际操作必须明确写出环境文件。

### 3.3 Windows 创建后部署

`new_app.py` 可以在 Windows 上使用；后续单 App 部署的等价命令是：

```powershell
.\scripts\app-deploy.ps1 -AppId erp -EnvFileName local.env.docker
```

它与 Linux 的 `app-deploy.sh` 具有相同目的：生成运行配置、构建并部署这个 App、刷新平台入口，并由后端执行 migration。

## 四、底层脚手架和平台检查命令

日常创建优先使用 `new_app.py`。下面的 `appctl.py` 是底层维护工具。

### 4.1 只生成 App 源码骨架

```bash
python3 scripts/appctl.py scaffold \
  --app erp \
  --name "ERP" \
  --description "企业资源管理" \
  --icon BriefcaseBusiness \
  --order 100
```

作用：只创建并校验 `apps/erp/` 骨架。

| 项目 | 结论 |
| --- | --- |
| 写入路径 | `apps/erp/` |
| Secret | 不创建 |
| Docker | 不操作 |
| 数据库 | 不操作 |

这是底层命令，不包含 `new_app.py` 的完整向导、并发锁、Secret 初始化和可选部署流程。普通开发者不要用它替代 `new_app.py`。

### 4.2 检查全部 App

检查 manifest、运行模型和现有 Secret：

```bash
python3 scripts/appctl.py check
```

只检查 Git 中应跟踪的配置，不要求本机已有 Secret：

```bash
python3 scripts/appctl.py check --skip-secrets
```

两条命令都只读，不写源码、不改容器、不改数据库。开发者的代码检查和 CI 通常使用 `--skip-secrets`；服务器部署前使用完整检查。

### 4.3 查看已登记的 App 和服务

```bash
python3 scripts/appctl.py apps
python3 scripts/appctl.py apps --json
python3 scripts/appctl.py services --app erp
```

作用：分别输出 App ID、供 CI 使用的 JSON App 列表，以及 ERP 拥有的 Compose 服务名。它们都是只读命令。

### 4.4 生成运行时配置

```bash
python3 scripts/appctl.py prepare
```

会校验现有 Secret，并写入：

```text
.runtime/apps-registry.json
.runtime/compose.apps.yaml
.runtime/nginx.conf
```

指定临时输出目录：

```bash
python3 scripts/appctl.py prepare --output-dir /tmp/erp-runtime-check
```

这时同名的三个文件写入指定目录。`prepare` 本身不启动或重建容器，也不修改数据库；它只生成配置文件。已经运行的容器不会因为单独执行 `prepare` 就全部刷新，正式变更应使用部署命令。

### 4.5 创建缺少的 Secret

只处理 ERP：

```bash
python3 scripts/appctl.py secrets ensure --app erp
```

处理全部 App：

```bash
python3 scripts/appctl.py secrets ensure
```

会写入 `secrets/apps/<app-id>/`。只创建缺少的文件，不覆盖已有 Secret 内容；同时会把 Secret 目录权限收紧为 `0700`，文件权限收紧为 `0600`。

它不写 App 源码、不操作 Docker、不修改数据库。不要为了“重新生成密码”而删除已有 `database-password.secret`；数据库账号中的旧密码不会因此自动改变。

## 五、开发和测试命令

### 5.1 后端 Python 环境

第一次准备 ERP 的本地后端环境：

```bash
python3 -m venv .local/venvs/erp
ERP_PYTHON="$(pwd)/.local/venvs/erp/bin/python"
"${ERP_PYTHON}" -m pip install -r apps/erp/backend/requirements.txt
```

会写入 `.local/venvs/erp/`，不修改 Docker 和生产数据库，也不应提交 Git。

修改 `models.py` 后生成 migration：

```bash
cd apps/erp/backend
"${ERP_PYTHON}" manage.py makemigrations
cd ../../..
```

会在下面的源码目录新增或修改 migration 文件：

```text
apps/erp/backend/<python-module>_api/migrations/
```

这些 migration 是 App 源码的一部分，必须和模型一起提交、打包和交付。不要只在临时容器里运行 `makemigrations`，否则生成文件可能不会回写到宿主源码。

后端检查：

```bash
.local/venvs/erp/bin/python apps/erp/backend/manage.py makemigrations --check --dry-run
.local/venvs/erp/bin/python apps/erp/backend/manage.py check
.local/venvs/erp/bin/python apps/erp/backend/manage.py test
```

这些命令不修改生产数据库。标准脚手架的宿主检查使用测试配置；测试可能创建并销毁自己的临时测试库。

### 5.2 前端依赖和构建

```bash
npm --prefix apps/erp/frontend ci
npm --prefix apps/erp/frontend run build
```

分别写入：

```text
apps/erp/frontend/node_modules/
apps/erp/frontend/dist/
```

它们不操作 Docker、不修改数据库。这两个目录是本地生成物，不进入 App ZIP，也不提交 Git。前端依赖版本应通过 `package.json` 和 `package-lock.json` 交付。

## 六、只部署一个 App

开发者本地：

```bash
scripts/app-deploy.sh erp local.env.docker
```

生产服务器：

```bash
scripts/app-deploy.sh erp server.env.docker
```

作用：部署当前 `apps/erp/` 源码，不重新生成骨架，不覆盖源码。

会执行：

1. 检查并补齐全部 App 缺少的 Secret。
2. 使用 `.runtime/platform-app-mutation.lock` 防止与其他 App 导入、部署或数据库操作并发，并在 `.runtime/app-deploy.erp.*` 生成候选运行配置。
3. 构建并启动 ERP 自己声明的服务。
4. 发布 `.runtime/apps-registry.json`、`.runtime/compose.apps.yaml` 和 `.runtime/nginx.conf`。
5. 强制重建 `auth-backend`、`gateway` 和 `portal-backend`，让新入口和路由生效。
6. ERP 后端启动时自动执行 migration。

影响范围：

| 项目 | 结论 |
| --- | --- |
| App 源码 | 不修改 |
| 运行文件 | 修改 `.runtime/`，可能创建缺少的 `secrets/apps/` 文件 |
| Docker | 构建 ERP 镜像，创建或重建 ERP 服务，并重建三个平台接入服务 |
| 数据库 | 会执行 ERP 新版本 migration；已有数据卷保留 |
| 自动数据库备份 | 没有 |

因此，已有 App 只替换源码后，不要直接部署。应先手工备份数据库，或者直接使用第九节的 `import_app.py --install --replace --deploy`，让导入器先自动备份。

部署失败时，脚本会尽量恢复旧运行配置、镜像和容器；已经成功执行的 migration、业务数据变化和外部副作用不会自动倒退。

部署脚本从构建阶段开始就属于有副作用的操作；即使镜像构建失败，回滚过程也可能重建目标 App 容器并让后端再次执行 migration。不要把它当作只读的“试构建”命令。Auth 和 Portal 后端被强制重建时，也会运行各自的启动检查和 migration。

部署后查看容器状态：

```bash
scripts/compose.sh --env-file local.env.docker ps
```

开发者本地默认入口通常是：

```text
http://localhost:8080/erp/
```

如果 `local.env.docker` 中的 `GATEWAY_HTTP_PORT` 不是 `8080`，把网址端口换成实际值。服务器使用实际域名或服务器地址，路径仍是 manifest 声明的 `/erp/`。

## 七、开发者打包 App

平台负责人必须先给开发者分配一个可信 Git tag 或 commit，例如 `app-sdk-v1`。开发者完成检查后运行：

```bash
python3 scripts/package_app.py erp --base app-sdk-v1
```

如果基准是当前远端主线，先更新远端引用：

```bash
git fetch origin
python3 scripts/package_app.py erp --base origin/main
```

`git fetch` 只更新本地仓库 `.git/` 中的远端引用，不替换当前工作区源码。检查完指定基准后再打包。

默认产物：

```text
export/erp.app.zip
```

自定义输出路径：

```bash
python3 scripts/package_app.py erp \
  --base app-sdk-v1 \
  --output export/erp-1.2.0.app.zip
```

作用和边界：

- 校验 App、Git 基准和从基准开始的改动范围。
- 默认发现 `apps/erp/` 之外有改动时拒绝打包。
- ZIP 内写入文件哈希、来源基准和共享平台依赖指纹。
- 输出文件已存在时拒绝覆盖。
- 不把 Secret、环境文件、本地数据库、`node_modules` 或 `dist` 放进包。
- 不修改 `apps/erp/`，不操作 Docker，不修改数据库。

ZIP 的 SHA-256 用于确认收到的字节是否和开发者报出的值一致，它不是开发者身份签名。哈希必须通过与 ZIP 不同的可信渠道交付。

开发者只交付 ZIP、命令打印的 SHA-256、基准 tag/commit、版本说明和测试结果。

## 八、服务器只验包，不安装

平台负责人先取得任务指定的基准：

```bash
git fetch origin --tags
```

再把开发者通过独立渠道提供的 64 位小写 SHA-256 填入命令：

```bash
APP_ZIP_SHA256='开发者单独提供的64位小写SHA256'
python3 scripts/import_app.py /path/to/erp.app.zip \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1
```

如果服务器已经安装 ERP，只读验包也必须明确允许“这是更新包”：

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --replace \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1
```

只验包时：

- 会在 `.runtime/app-import.*` 建立私有临时目录，完成后清理。
- 不写入或替换 `apps/erp/`。
- 不创建、停止或重建容器。
- 不读取或修改 App 数据库。
- 不执行 ZIP 中的 App 代码，但这不等于第三方代码已经安全。

验包后仍要人工审查 Dockerfile、Python/npm 依赖、权限代码和 migration，并先在没有生产 Secret、没有生产数据的隔离环境构建测试。

当前工具会验证文件哈希、manifest、运行结构、来源基准和共享依赖兼容性，但不会像 Git 一样显示逐文件、逐行的新旧差异，也不会自动合并服务器上的本地修改。更新包是完整 App 目录版本。

## 九、服务器安装或更新 App

### 9.1 安装全新 App，只放源码

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1 \
  --yes
```

会写入：

```text
apps/erp/
.runtime/import-receipts/
.runtime/platform-app-mutation.lock
```

验包和安装期间还会使用 `.runtime/app-import.*` 临时目录，正常结束后清理。导入器会根据服务器现有 App 重新分配不冲突的 IPAM，并把实际值写入安装后的 `apps/erp/app.manifest.yaml`。它不部署容器、不创建 Secret、不创建数据库、不执行 migration。

### 9.2 安装全新 App 并部署

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --deploy \
  --env-file server.env.docker \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1 \
  --yes
```

除 9.1 的源码和回执外，还会：

- 创建缺少的 Secret 和 `.runtime/` 运行配置。
- 构建镜像，创建容器、网络和数据库卷。
- 刷新 Auth、网关和 Portal 接入。
- 自动执行新 App 的 migration，创建数据库表。

“服务器没有 `apps/erp/`”不等于 Docker 中一定没有 ERP 历史数据。以前删除过源码或执行过不带 `-v` 的 `docker compose down` 时，同名命名数据卷可能仍存在，新安装可能复用旧卷。首次部署前，平台负责人必须检查历史安装记录和 `docker volume ls`，不得把来源不明的旧卷当作全新空数据库。

### 9.3 更新已有 App，只替换源码

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --replace \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1 \
  --yes
```

会执行完整目录的原子替换，并写入：

```text
apps/erp/                         新版本源码
.runtime/import-backups/          替换前的旧版本源码快照
.runtime/import-receipts/         本次导入回执
.runtime/platform-app-mutation.lock
```

旧源码快照使用私有随机目录保存，供故障恢复和审计。原子替换要求 Linux 支持 `renameat2(RENAME_EXCHANGE)`，并要求 `apps/` 与 `.runtime/` 位于同一文件系统；预检不满足时会在替换前失败。

这个命令不操作容器、不执行 migration，也不会自动备份数据库。当前正在运行的容器仍保持原运行状态，但服务器磁盘上的 `apps/erp/` 已经是新版本。之后部署前必须先备份数据库。

如果先用本节命令替换源码，之后再单独执行 `app-deploy.sh`，部署失败时 `app-deploy.sh` 只恢复运行配置、镜像和容器，不会自动把 `apps/erp/` 换回旧源码。只有把替换和部署放在同一次 9.4 命令中，导入器才会在部署失败时尝试自动交换回旧源码。

### 9.4 更新已有 App、自动备份并部署

生产服务器推荐使用：

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --replace \
  --deploy \
  --env-file server.env.docker \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1 \
  --yes
```

实际顺序是：

1. 验证 ZIP、SHA-256、Git 基准、共享依赖和标准运行结构。
2. 使用 `pg_dump` 备份现有 ERP 数据库，并用 `pg_restore --list` 校验备份。
3. 原子替换整个 `apps/erp/`，旧源码保存到 `.runtime/import-backups/`。
4. 部署新源码、刷新平台入口。
5. 新后端启动时执行新版本随包交付的 migration。
6. 写入 `.runtime/import-receipts/` 回执。

数据库备份默认写入：

```text
backups/apps/erp/erp-db-<UTC时间>.dump
```

所以，对已有 App 来说，本质是“验证完整的新 App 包 -> 先备份旧数据库 -> 完整替换旧源码 -> 运行新版本 migration”。它不是 Git 合并。

导入器也不会判断 ZIP 在业务含义上比服务器版本“更新”还是“更旧”。版本先后关系、多人代码合并和发布审批必须在中央 Git 与团队流程中完成，服务器导入器只负责验证并应用负责人指定的完整包。

如果部署失败，工具会尽量恢复旧源码、运行配置、镜像和容器；数据库 migration 和业务写入不会自动恢复。需要回退数据库时，必须由负责人使用第十节的恢复命令，并确认备份版本和旧代码匹配。

## 十、数据库备份和恢复

本节工具只处理 App manifest 中唯一的 PostgreSQL 数据库。它不备份或恢复上传文件、media、Redis、其他 Docker volume、对象存储、消息队列或外部系统，也不提供这些系统之间的一致性快照。业务同时使用这些数据源时，负责人必须另做配套备份和恢复方案。

### 10.1 手工备份一个 App 数据库

生产服务器：

```bash
python3 scripts/backup_app_db.py erp \
  --env-file server.env.docker
```

开发者本地：

```bash
python3 scripts/backup_app_db.py erp \
  --env-file local.env.docker
```

默认写入：

```text
backups/apps/erp/erp-db-<UTC时间>.dump
```

指定输出文件：

```bash
python3 scripts/backup_app_db.py erp \
  --env-file server.env.docker \
  --output backups/apps/erp/before-1.2.0.dump
```

命令会使用 `.runtime/platform-app-mutation.lock`，重新生成 `.runtime/` 配置，读取正在运行的 PostgreSQL，生成 custom-format dump，再用 `pg_restore --list` 校验归档。它不修改数据库内容、不重建容器、不修改 App 源码；输出文件已存在时拒绝覆盖。

备份期间后端仍可能继续写入数据库，恢复命令创建“恢复前安全备份”时也会先备份、再停止后端。要求严格恢复点或还要同步文件、缓存、外部系统时，应先进入维护窗口并停止全部写入者。

### 10.2 只验证备份，不恢复

```bash
python3 scripts/restore_app_db.py erp \
  backups/apps/erp/before-1.2.0.dump \
  --env-file server.env.docker
```

作用：检查归档目录是否能被 PostgreSQL 工具识别，并打印恢复计划。它会使用 `.runtime/platform-app-mutation.lock`、更新 `.runtime/` 配置，并在 `.runtime/database-restore/` 建立私有临时快照，结束后清理；不会恢复数据库，不会停止后端，不会修改源码。

`pg_restore --list` 成功只证明归档目录可以解析，不保证全部数据块、扩展、权限和 PostgreSQL 版本在正式恢复时都兼容，所以仍然必须先做非生产恢复演练。

### 10.3 正式恢复数据库

只有完成非生产恢复演练并取得审批后才执行：

```bash
python3 scripts/restore_app_db.py erp \
  backups/apps/erp/before-1.2.0.dump \
  --env-file server.env.docker \
  --restore \
  --yes
```

它会：

1. 再次验证归档。
2. 先把当前数据库备份到 `backups/apps/erp/`，作为恢复前安全备份。
3. 停止 ERP 后端容器。
4. 使用单事务清理归档中包含的旧对象，再恢复归档中的 ERP PostgreSQL 对象。
5. 重启 ERP 后端并等待健康检查通过。

这是破坏性数据库操作。工具使用 `pg_restore --clean --if-exists`，不会删除并重建整个数据库；只清理归档列出的对象，归档中不存在的额外对象可能继续保留。因此不能把它理解成整库精确克隆。

`--health-timeout SECONDS` 可设置重启后的健康等待时间。恢复数据库不会自动替换 App 源码；后端重启后还会按当前代码再次执行 migration，负责人必须确保运行代码、migration 历史和 dump 属于兼容版本。

恢复前安全备份只会打印和保留路径，不会在后续失败时自动回灌。如果数据库恢复已经提交、但后端重启或健康检查随后失败，命令仍会返回非零。此时不能因为“命令失败”就认定数据库没变，也不能盲目重试；必须先判断失败阶段，再决定是否人工回灌安全备份。

## 十一、整个平台的启动、停止和状态

### 11.1 启动全部服务

开发者本地：

```bash
scripts/docker-up.sh local.env.docker
```

生产服务器：

```bash
scripts/docker-up.sh server.env.docker
```

它会：

- 如果环境文件不存在，从同名 `.example` 或 `.env.docker.example` 复制一份。
- 创建全部缺少的 App Secret。
- 重写 `.runtime/apps-registry.json`、`.runtime/compose.apps.yaml` 和 `.runtime/nginx.conf`。
- 对平台完整 Compose 模型执行 `up -d --build`；只启动缺失或停止的服务，并按镜像或配置变化重建受影响容器。
- 被启动或重建的 Django 后端会执行 migration。

因此它会改变 Docker 状态，也可能改变多个 App 的数据库结构。它不是“只启动刚新增的 App”的命令。

`docker-up.sh` 不等待全部服务健康后再退出。命令结束后仍要执行 `scripts/compose.sh --env-file <环境文件> ps` 检查健康状态。

### 11.2 查看状态和日志

```bash
scripts/compose.sh --env-file server.env.docker ps
scripts/compose.sh --env-file server.env.docker logs -f erp-backend
```

`compose.sh` 会先执行 `appctl.py prepare`，所以即使 `ps` 和 `logs` 是只读 Docker 操作，也会重写 `.runtime/` 的三个生成文件。它不改 App 源码；上面两个示例不改数据库。

`compose.sh` 会把后面的参数原样传给 `docker compose`。如果把 `ps`、`logs` 换成 `up`、`down`、`exec` 等命令，副作用由对应 Docker Compose 命令决定。

`compose.sh` 不会自动选择 `local.env.docker` 或 `server.env.docker`，所以每次都应像示例一样明确写 `--env-file`，避免读取了错误的 Shell 或默认 `.env` 配置。

`compose.sh`、`docker-up.sh` 和 `docker-down.sh` 不使用 App 全局变更锁。平台负责人必须人工保证它们不与 `new_app`、`import_app`、`app-deploy`、数据库备份或恢复并发执行。

### 11.3 停止全部服务

```bash
scripts/docker-down.sh server.env.docker
```

默认会停止并删除 Compose 容器和网络，但保留命名数据卷，所以 PostgreSQL 数据仍在。如果 `.runtime/compose.apps.yaml` 不存在，脚本会先运行 `appctl.py prepare`。

不要日常执行：

```bash
scripts/docker-down.sh server.env.docker -v
```

`-v` 会删除完整平台 Compose 模型中的命名数据卷，其中包括 App 的 PostgreSQL、Redis 和 media 数据，可能造成永久丢失。只有明确要销毁整套环境并已验证外部备份时才允许使用。`scripts/compose.sh --env-file server.env.docker down -v` 具有同样风险。

## 十二、危险参数和能力边界

下面这些参数不是普通流程的兼容开关：

| 参数 | 风险 |
| --- | --- |
| `package_app.py --allow-outside-changes` | App 目录外有修改仍强行打包；包会记录该例外，并被导入器默认拒绝 |
| `import_app.py --allow-runtime-changes` | 接受偏离标准脚手架的运行文件或部分 Compose 设置，需要单独安全审查；永久禁止的 schema 和安全限制仍不能绕过 |
| `import_app.py --allow-unverified-source` | 绕过不可用或不可信 Git 基准以及“包外有改动”来源检查；仍不能绕过共享平台依赖指纹不一致 |
| `import_app.py --skip-db-backup` | 更新并部署已有 App 时跳过数据库备份，migration 失败后可能无法恢复 |
| 验包时省略 `--expected-sha256` | 只能计算收到的 ZIP 哈希，不能与独立渠道提供的可信哈希核对 |
| `restore_app_db.py --restore --yes` | 跳过人工输入并实际清理、恢复数据库对象；`--yes` 不是审批记录 |
| `docker-down.sh ... -v` 或 `compose.sh ... down -v` | 删除整个平台的命名数据卷，可能删除 PostgreSQL、Redis 和 media 数据 |

正式协作流程禁止开发者使用 `--allow-outside-changes`。其余三个导入例外参数只能由平台负责人逐项审查后使用；正常安装和更新都不应带这些参数。

`--yes` 只跳过交互确认，不跳过文件、安全、manifest、哈希或运行模型检查，但它会让安装和恢复无需人工再次输入确认。执行前仍要逐字核对 App ID、ZIP、环境文件和命令模式。

当前能力边界：

- 能创建标准骨架、部署、打包、验包、安装新 App 和替换已有 App。
- 能验证 ZIP 完整性、来源基准、共享平台兼容性和标准运行结构。
- 能在“替换已有 App 并部署”时自动备份 PostgreSQL，再运行新版本 migration。
- 不能显示 Git 式逐行差异，不能自动合并服务器和 ZIP 双方的修改。
- 不能自动判断 ZIP 的业务版本一定比服务器版本新，版本选择由负责人和中央 Git 决定。
- 不能保证代码回滚会自动回滚数据库 migration、业务数据或外部系统副作用。
- 数据库工具不能覆盖 PostgreSQL 之外的文件、缓存、其他 volume 和外部系统。
- 不能把 Secret、数据库 dump、环境文件或本地生成目录当作 App 源码一起交付。

## 十三、小白照着执行的完整流程

### 开发者

以下假设开发者电脑已经有 `local.env.docker`。第一次初始化整个平台时，先按第 11.1 节运行 `scripts/docker-up.sh local.env.docker`；脚本会在文件不存在时从示例创建它，生产使用前必须人工检查配置。

下面是 Linux/macOS 命令。Windows 的虚拟环境和 PowerShell 部署写法见 [开发与部署流程](./开发与部署流程.md)；Python 打包命令的参数相同。

```bash
python3 scripts/new_app.py erp --name "ERP" --no-deploy --yes
python3 -m venv .local/venvs/erp
.local/venvs/erp/bin/python -m pip install -r apps/erp/backend/requirements.txt
scripts/app-deploy.sh erp local.env.docker
python3 scripts/appctl.py check --skip-secrets
.local/venvs/erp/bin/python apps/erp/backend/manage.py makemigrations --check --dry-run
.local/venvs/erp/bin/python apps/erp/backend/manage.py check
.local/venvs/erp/bin/python apps/erp/backend/manage.py test
npm --prefix apps/erp/frontend ci
npm --prefix apps/erp/frontend run build
python3 scripts/package_app.py erp --base app-sdk-v1
```

把 `export/erp.app.zip`、SHA-256、`app-sdk-v1`、版本说明和测试结果交给平台负责人。

### 服务器第一次安装

```bash
APP_ZIP_SHA256='开发者单独提供的64位小写SHA256'
python3 scripts/import_app.py /path/to/erp.app.zip \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1

python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --deploy \
  --env-file server.env.docker \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1 \
  --yes
```

### 服务器更新已有 App

```bash
APP_ZIP_SHA256='开发者单独提供的64位小写SHA256'
python3 scripts/import_app.py /path/to/erp.app.zip \
  --replace \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1

python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --replace \
  --deploy \
  --env-file server.env.docker \
  --expected-sha256 "${APP_ZIP_SHA256}" \
  --expected-base app-sdk-v1 \
  --yes
```

第一次安装成功或服务器重新分配 IPAM 后，平台负责人还要把服务器实际的 `apps/erp/` 提交回中央 Git，让后续开发者基于真实版本继续开发。
