# 基础目录结构

以下以 App ID `erp` 为例。

使用标准命令创建这套目录，避免复制旧 App 时带入历史差异：

```bash
python3 scripts/new_app.py erp --name ERP --no-deploy --yes
```

```text
apps/erp/
├── AGENTS.md
├── app.manifest.yaml
├── README.md
├── backend/
│   ├── Dockerfile
│   ├── manage.py
│   ├── requirements.txt
│   ├── mj_backend/
│   │   ├── __init__.py
│   │   ├── settings.py
│   │   ├── urls.py
│   │   ├── asgi.py
│   │   └── wsgi.py
│   └── erp_api/
│       ├── __init__.py
│       ├── apps.py
│       ├── models.py
│       ├── platform.py
│       ├── urls.py
│       ├── views.py
│       ├── tests.py
│       └── migrations/
│           └── __init__.py
└── frontend/
    ├── Dockerfile
    ├── nginx.conf
    ├── package.json
    ├── package-lock.json
    ├── vite.config.ts
    ├── index.html
    └── src/
        ├── config.js
        ├── api.js
        ├── session.js
        ├── main.js
        ├── App.vue
        └── styles.css
```

上面是脚手架实际生成的完整基础结构。`AGENTS.md` 会告诉后续编码助手只能修改当前 App，并重申数据库、路由和跨 App API 边界。随着业务增长，可在 `erp_api/` 下增加 `services/`、`permissions/` 或独立 `tests/`，也可在 `frontend/src/` 下增加 `apps/`、`components/`、`assets/` 和 `styles/`。这些是按需扩展目录，不是脚手架的默认产物。

下面五个部分应当完整交付：

```text
app.manifest.yaml
AGENTS.md
README.md
backend/
frontend/
```

`apps/erp/` 是唯一允许开发者拥有的源码边界，但 ZIP 不是手工压缩这个目录。标准打包器还会在 ZIP 根部加入一份带文件大小和 SHA-256 的 `app-package.json`：

```text
erp.app.zip
├── app-package.json
└── apps/
    └── erp/
        └── ...
```

Linux 和 macOS 的打包命令相同，运行 `python3 scripts/package_app.py erp --base app-sdk-v1`；Windows 运行 `py -3 scripts/package_app.py erp --base app-sdk-v1`。`app-sdk-v1` 必须换成负责人指定的可信 tag/commit。平台负责人使用 `import_app.py` 校验协议 v2 元数据、共享平台依赖指纹和每个文件，不接受来源不明的普通 ZIP 或旧 v1 包直接覆盖生产目录。

## app.manifest.yaml

这是 App 的平台登记表，负责声明：

- App ID、名称、说明、图标和排序。
- 门户入口和默认可见范围。
- 前端、后端和 PostgreSQL 容器。
- 页面路由、API 路由和附件路由。
- Auth 内部服务名称。
- 数据卷、网络和 Secret 挂载。

真实密码不得写入清单。清单里只能写 Secret 文件名和使用它的服务。

## backend

后端负责：

- 数据库模型和迁移。
- API 接口。
- 业务权限和数据范围。
- 调用 Auth 验证登录身份。
- 文件上传、下载和后端测试。

后端只能连接自己的数据库，不得直接连接 Auth、CRM 或其他 App 的数据库。

`mj_backend/` 是 Django 项目配置；`erp_api/` 是业务 App。`platform.py` 只做公共 Auth/同源保护的 App 级适配，不复制公共实现。`models.py` 变更后必须生成并提交 migration，不得依赖 `syncdb` 长期演进表结构。

新增 Python 库必须写入 `requirements.txt` 并锁定经过测试的版本。本地虚拟环境、`db.sqlite3`、`__pycache__`、日志、数据库 dump 和上传文件都不是源码，禁止交付。

## frontend

前端负责：

- 页面和交互。
- 调用本 App 后端接口。
- 展示 Auth 返回的当前登录人。
- 监听登录、退出和代理身份变化。
- 未保存离开提醒和统一页面规范。

前端不得保存或判断系统级白名单，也不得信任浏览器传入的管理员标记。

`nginx.conf` 负责把 `/<app-id>/assets/` 映射到构建产物的 `/assets/`，并让 App 页面子路径回退到 `index.html`；每个 App 使用自己的配置，不在共享 Nginx 中追加 App 名称。`config.js` 负责 API 根地址，`session.js` 接入公共会话存储，`api.js` 接入统一请求和认证恢复；`main.js`、`App.vue`、`styles.css` 分别是启动入口、根组件和初始全局样式。

刚开始做页面时，只需要记住两个入口：页面内容和交互改 `App.vue`，布局、颜色和响应式样式改 `styles.css`。除非后端接口或登录方式发生变化，否则不要先改 `api.js`、`session.js` 和 `config.js`。

新增 npm 库必须同时更新 `package.json` 和 `package-lock.json`。`node_modules`、`dist`、测试报告和本地 `.env` 禁止交付；服务器会用 `npm ci` 和 Dockerfile 重新构建。

Auth 接入还必须遵守：

- App 后端只消费 introspect 返回的 `canUseSystemAdmin`，不得再组合判断 `isSystemAdmin` 或本地白名单。
- 账号禁用由 Auth 拒绝登录和 Token，App 不做白名单绕过或重复补偿。
- 浏览器写请求必须经过同源校验；`same-site` 其他子域和 `cross-site` 请求统一返回 `CROSS_ORIGIN_WRITE_BLOCKED`。
- 业务请求收到 `401` 后，前端先用浏览器当前 Cookie 调 Auth 会话校验；当前会话仍有效时不得清会话或跳登录。
- 部门/人员权限选择必须保存并提交目录的 `orgRevision`，组织版本变化时拒绝覆盖并要求重新选择。
- 部门树、人员多选、包含子部门、排除人员和生效成员表必须遵守 [统一组织权限页面与接口规范](../统一组织权限页面与接口规范.md)，不得重新实现扁平单选列表。

## README.md

每个 App 建议有自己的 README，至少说明：

- App 的用途。
- 主要页面和接口。
- 数据库归属。
- 权限规则。
- 测试命令。
- 特殊外部依赖。

## 不属于 App 交付物

以下内容由每台机器独立持有：

```text
local.env.docker / server.env.docker
secrets/apps/erp/
.runtime/
Docker volumes
本地测试数据和生产业务数据
上传文件、缓存、日志和 backups/
```

数据库表结构通过 migration 交付；默认数据通过 data migration、fixture 或管理命令交付。真实业务数据必须走单独的加密迁移流程，不能塞进 App 文件夹。
