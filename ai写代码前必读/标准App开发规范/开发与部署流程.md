# 开发与部署流程

以下仍以 App ID `erp` 为例。

## 平台负责人第一次登记 ERP

多人协作时，平台负责人先分配唯一 App ID `erp` 和基准 commit/tag，但不把空骨架提前合进生产服务器跟随的 `main`。开发者从该基准创建任务分支，再在自己的电脑运行：

```bash
python3 scripts/new_app.py erp \
  --name ERP \
  --description "企业资源管理" \
  --icon BriefcaseBusiness \
  --order 100 \
  --no-deploy \
  --yes
```

该命令会生成并校验 ERP。开发者可把 `apps/erp/` 提交到自己的任务分支用于协作，但生产验收前不合并进 `main`。平台负责人收到标准包后在服务器做首次安装，成功后再把服务器实际目录提交回中央 `main`。

单人直接在目标机器操作时，也可运行 `python3 scripts/new_app.py erp` 使用向导。向导默认只创建、不部署；部署必须明确选择，并区分环境：开发者电脑传 `--env-file local.env.docker`，生产服务器传 `--env-file server.env.docker`。

它在 Git 工作区只创建：

```text
apps/erp/
```

如果目录已存在，命令直接失败且不会覆盖文件。生成完成后，只在该目录内编写业务模型、权限、接口和页面。

如果首次校验或部署失败，生成目录不会被删除。按向导最后打印的 `appctl.py check` 和 `app-deploy` 命令恢复，不要重新生成同名 App。

向导即使不部署，也会在当前机器自动生成 ERP 自己的 Secret。底层等价命令是：

```bash
python3 scripts/appctl.py secrets ensure --app erp
```

通常会生成：

```text
secrets/apps/erp/django.secret
secrets/apps/erp/database-password.secret
secrets/apps/erp/auth-introspection.secret
```

向导也会检查全部 App 清单和 ERP Secret。平台维护时仍可手工检查全部 Secret：

```bash
python3 scripts/appctl.py check
```

后续修改 ERP 后，只部署 ERP：

```bash
scripts/app-deploy.sh erp server.env.docker
```

查看状态：

```bash
scripts/compose.sh --env-file server.env.docker ps
```

应当看到 ERP 自己的服务正常运行：

```text
erp-frontend
erp-backend
erp-postgres
```

## 后续修改 ERP

开发者本地修改 ERP 的页面、接口、数据库模型或 `app.manifest.yaml` 后，运行：

```bash
scripts/app-deploy.sh erp local.env.docker
```

生产服务器由平台负责人验收、备份后使用 `server.env.docker`；开发者不应持有生产环境文件。

该命令会：

1. 检查并补齐缺少的 Secret。
2. 重新读取全部 App 清单。
3. 同步 ERP 的 Auth 内部服务凭据。
4. 构建和启动 ERP 自己的容器。
5. 刷新网关路由。
6. 不重建 CRM 和其他无关业务 App。

部署会分阶段检查 App 健康状态、Compose 模型和 Nginx 配置。任一阶段失败时，应恢复上一版运行时配置、App 镜像和容器，不得把失败容器留在线上。

## 数据库迁移

修改 `backend/<app-module>_api/models.py` 后，必须先在仓库忽略的 `.local/venvs/erp/` 安装 App 自己的 Python 依赖，再在宿主源码目录生成并检查 migration。Linux 和 macOS 的宿主 Python 命令相同：

```bash
python3 -m venv .local/venvs/erp
ERP_PYTHON="$(pwd)/.local/venvs/erp/bin/python"
"${ERP_PYTHON}" -m pip install -r apps/erp/backend/requirements.txt
cd apps/erp/backend
"${ERP_PYTHON}" manage.py makemigrations
"${ERP_PYTHON}" manage.py makemigrations --check --dry-run
"${ERP_PYTHON}" manage.py check
"${ERP_PYTHON}" manage.py test
cd ../../..
```

Windows PowerShell：

```powershell
py -3 -m venv .\.local\venvs\erp
$ErpPython = (Resolve-Path .\.local\venvs\erp\Scripts\python.exe).Path
& $ErpPython -m pip install -r .\apps\erp\backend\requirements.txt
Push-Location .\apps\erp\backend
& $ErpPython manage.py makemigrations
& $ErpPython manage.py makemigrations --check --dry-run
& $ErpPython manage.py check
& $ErpPython manage.py test
Pop-Location
```

migration 文件必须和模型一起提交。`RUN_SYNCDB` 只用于初始化没有迁移历史的表，不能替代后续 schema migration。

不要只在临时容器里执行 `makemigrations`，否则文件不会自动写回宿主源码。脚手架的宿主检查默认使用内存 SQLite，只用于生成和检查 migration；本地 `app-deploy` 才会在 Docker PostgreSQL 中执行实际 migration。显式配置文件型 SQLite 时，不得把生成的数据库交付，打包器会直接拒绝。

服务器部署时，后端 entrypoint 会自动执行 migration。容器部署失败可以恢复上一版镜像和容器，但已经修改的数据库不会自动恢复，所以更新已有 App 前必须先备份该 App 数据库。

## 本地验收和打包

前端宿主检查需要 Node.js 22 LTS 和随附 npm，平台 Python 命令使用 Python 3.11 至 3.14。交付前至少执行：

```bash
python3 scripts/appctl.py check --skip-secrets
.local/venvs/erp/bin/python apps/erp/backend/manage.py makemigrations --check --dry-run
.local/venvs/erp/bin/python apps/erp/backend/manage.py check
.local/venvs/erp/bin/python apps/erp/backend/manage.py test
npm --prefix apps/erp/frontend ci
npm --prefix apps/erp/frontend run build
```

回到仓库根目录生成标准包：

```bash
python3 scripts/package_app.py erp --base app-sdk-v1
```

把 `app-sdk-v1` 换成任务实际指定的 tag 或完整 commit；基于当前远端主线时，先 `git fetch origin` 再写 `--base origin/main`。打包器会检查从该基准开始的全部 Git 变化，发现 `apps/erp/` 以外的修改就拒绝打包。

在仓库由另一个账号创建、CI 挂载目录或受限账号执行时，打包器仍会忽略用户级 Git 配置，但会给 Git 注入当前已解析仓库根这一条精确的 `safe.directory`。它不会修改全局配置，也不会信任其他目录；禁止为了省事运行 `git config --global --add safe.directory '*'`。

Windows 打包会使用可写临时 ZIP 描述符完成刷新，再在同一文件身份上计算 SHA-256 和执行发布前校验。Windows 不支持目录 `fsync` 时只会在发布后记录耐久性警告，不会把已经成功发布且校验通过的 ZIP 误报为失败。

产物为协议 v2 的 `export/erp.app.zip`，包含可信基准和共享平台依赖指纹。开发者只交这个 ZIP、SHA-256、基准 commit/tag、版本说明和测试结果，不交 Secret、环境文件、本地数据库、`node_modules` 或 `dist`。旧 v1 包必须用当前工具重新生成。

## 平台负责人验包和安装

先做不落盘、不执行 App 代码的包校验：

```bash
git fetch origin --tags
APP_ZIP_SHA256='把开发者单独发送的64位小写SHA256填在这里'
python3 scripts/import_app.py /path/to/erp.app.zip \
  --expected-sha256 "$APP_ZIP_SHA256" \
  --expected-base app-sdk-v1
```

`APP_ZIP_SHA256` 是开发者通过独立渠道提供的 64 位小写 ZIP 哈希。已有 App 的更新包在只读验收时也要加 `--replace`。

之后仍须人工审查 Dockerfile、依赖、权限和 migration，并在无生产 Secret、无生产数据的隔离环境构建测试。

导入器默认要求前后端 Dockerfile 和 manifest `build` 定义与脚手架完全一致。普通依赖变化不需要改这些文件；如果确有自定义运行需求，必须单独审查后显式使用高风险 `--allow-runtime-changes`，不能把它当作普通兼容开关。

导入器也会比对包内和服务器的共享平台依赖指纹，并默认拒绝曾用 `--allow-outside-changes` 打出的包。只有平台负责人完成逐项审查后，才可在只读验包或安装时加 `--allow-unverified-source`；正常流程禁止这两个来源逃生参数，且它们不能绕过指纹不一致。

新 App 只安装源码：

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --expected-sha256 "$APP_ZIP_SHA256" \
  --expected-base app-sdk-v1 \
  --yes
```

导入器会按服务器已有 App 重新分配唯一 IPAM，再把 App 放入 `apps/erp/`。完成审查和隔离测试后，也可以安装并部署：

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --deploy \
  --env-file server.env.docker \
  --expected-sha256 "$APP_ZIP_SHA256" \
  --expected-base app-sdk-v1 \
  --yes
```

更新已有 App 必须显式 `--replace`。推荐直接使用下面的组合命令；它会在替换源码前自动备份数据库，不需要再手工重复备份：

```bash
python3 scripts/import_app.py /path/to/erp.app.zip \
  --install \
  --replace \
  --deploy \
  --env-file server.env.docker \
  --expected-sha256 "$APP_ZIP_SHA256" \
  --expected-base app-sdk-v1 \
  --yes
```

`import_app` 的替换部署流程会调用 App 数据库备份；`pg_dump` 后还会自动用 `pg_restore --list` 验证归档，任何备份或归档验证失败都会阻止部署。备份默认写入 `backups/apps/erp/`，不进入 Git 或 App 包。只有先用 `--install --replace` 只替换源码、稍后直接运行 `app-deploy` 时，才需要在部署前手工执行 `python3 scripts/backup_app_db.py erp --env-file server.env.docker`。同一次 `import_app --install --replace --deploy` 失败时会尝试恢复旧源码、运行配置、镜像和容器；分开执行时，后续 `app-deploy` 失败不会自动把源码换回旧版。两种流程都不会自动倒退 migration、业务数据和外部副作用。

恢复前先用 `python3 scripts/restore_app_db.py erp <dump> --env-file server.env.docker` 只验证归档和计划；经过非生产演练和审批后，才加 `--restore --yes`。工具会先备份当前数据库、停止后端、单事务恢复、重启并检查健康，失败信息会保留并打印安全备份路径。

## secrets ensure 会不会覆盖密码

不会。

重复运行：

```bash
python3 scripts/appctl.py secrets ensure
```

如果文件已经存在，命令保留原内容，只确保文件存在并把权限收紧为 `0600`。常见输出：

```text
App secrets ready: 0 created, 20 already present
```

只有清单新增了一种 Secret，并且对应文件还不存在时，才会创建新文件。

## 禁止操作

不要直接执行下面这些操作：

```text
把密码写进 .env
把密码写进 app.manifest.yaml
提交 secrets/apps/ 到 Git
删除已有 database-password.secret 后重新生成
手工给 Nginx 增加新 App 路由
手工给门户增加新 App 名称或图标
手工给 Auth 增加服务密钥环境变量
为新增 ERP 修改 CRM 代码
```

## Git 提交范围

正常新增 ERP 时，Git 中应主要出现：

```text
apps/erp/
```

下面两个目录是运行时自动生成内容，不应出现在 Git 提交中：

```text
.runtime/
secrets/apps/
```

生产验收成功后，平台负责人必须把服务器实际安装的 `apps/erp/` 提交回中央 Git。导入器可能已重新分配 IPAM；只有回写中央仓库，后续开发者才能看到真实的 App、路由和网段占用。
